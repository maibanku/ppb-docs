# PPB IAM · 需求基线

> v0.4 · 2026-10-27 · 目标设计，待实施。

## 1. 产品与架构

自研Go统一账号认证中心，参考MaxKey产品形态。同仓server-iam独立部署，内部account/profile/identity/credential/authentication/oauthserver/session/application/platformauthz/audit模块化。将来可拆独立ppb-iam仓库，保持身份与协议连续。

统一用户主体同时服务普通用户与平台管理员，保留既有user_id和user_biz_key。公共资料不再通过独立server-user建立第二套用户主体。user_name等旧列如何迁移以迁移计划为准。

## 2. 权威边界

| 服务 | 责任 |
|---|---|
| server-iam / ppb_iam | 全局用户、公共资料、登录标识、密码/MFA、协议、客户端、认证会话、平台管理员和分域角色菜单按钮 |
| server-im / ppb_im | 聊天组织、成员、部门、邀请、组织角色、聊天偏好与业务会话 |
| server-camera / ppb_camera | 相机业务账号、私有资料、偏好、业务会话；额度作品由现有业务模型管理 |
| wardrobe服务 / ppb_wardrobe | 衣橱账号、身材等私有资料与偏好；具体工程待建 |
| server-gateway / 业务后端 | 凭证验证、可信身份、操作权限及资源范围检查 |

不首建IAM企业组织/目录组。chat工作空间不是认证租户，应用域不是组织。平台全局停用影响全部访问，业务停用只影响对应账号/组织。公共昵称头像是默认值，业务覆盖值独立维护。

## 3. 用户和管理员

普通账号自助注册不创建platform_admins。IAM管理员与平台运营管理员均为平台管理资格加不同应用域角色；聊天组织管理员来自chat成员角色，不能进入平台后台。is_super保留在platform_admins，表示受保护治理资格，不自动读取敏感业务内容。

平台菜单/按钮直接分配给角色，人员只关联角色；更新角色批量生效，禁止逐人维护菜单。菜单节点映射到后端权限，不维护第二套platform_role_permissions。

## 5. 数据与发布原则

默认不合并同邮箱账号，不改变消息文件订单归属。认证成功仍检查应用准入、管理资格、角色、资源范围。客户端隐藏按钮不是安全边界；时限、撤权传播上限、缓存TTL和依赖版本在P0固定后验收。

SQL只覆盖账号/认证/授权及业务用户扩展，58表不是完整业务数据库。所有字段至少两个单词下划线连接，沿用雪花主键、表专属业务键、公共时间/软删列、逻辑关联和KV规范。

实施阶段：P0锁定契约和迁移，P1测试认证闭环，P2管理端试点，P3普通业务接入，P4旧服务退役。按照[验收门槛](ac/00-验收总则与发布门槛.md)留证，不以文档替代实现。
