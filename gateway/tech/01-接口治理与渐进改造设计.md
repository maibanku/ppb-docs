# 网关接口治理与渐进改造设计

## 1. 对当前代码的结论

推荐渐进改造，而不是全面重写、引入动态 RPC 暴露或立即拆出多个网关。当前已具备分域注册、类型化调用、Proto 描述符和管理端权限策略，应复用这些资产。

核查基线：2026-11-06 本地 `ppb-base` HEAD `302b184`。开始实施时必须重新核实 HEAD 与工作区；该基线不代表后续实时状态。

| 现有文件 | 已有能力 | 需要处理 |
|---|---|---|
| `server-gateway/main.go` | 装配 user/manage/im/todo/camera；缺失管理策略拒绝启动 | 将完整目录校验纳入装配；保留当前守卫 |
| `proxy/method_registry.go` | 精确/模板注册、描述符、策略、路由查询 | 冲突检测、确定性匹配、完整元数据 |
| `proxy/registry_im.go`、`registry_todo.go` 等 | 按域手写 HTTP→RPC 参数绑定 | 分域契约驱动生成，减少重复维护 |
| `proxy/policy.go` | self/app_perm/super_gov；策略非法拒绝启动 | 区分身份类别与授权规则，复用现有策略语义 |
| `gateway_routes.go` | 白名单、认证、安全链、特殊入口 | 清点 Registry 之外的入口，避免目录遗漏 |
| `swagger/swagger.go` | 根据 Registry 描述符生成 OpenAPI 3.0、接口清单 | 补齐身份、权限、参数来源及特殊入口描述 |
| `buf.gen.yaml`、`idl/buf.yaml` | 已配置 Go/gRPC 生成 | 增量增加并锁定 HTTP 生成依赖 |
| `proxy/grpc_clients.go` | 各业务客户端装配、可信调用上下文 | 保留实际服务归属，避免按 Proto 包猜目标服务 |

特别注意：todo 复用 server-im；legacy UserService 的 UserIam 与 UserOrg 分别承接到 IAM 和组织域。仅按 RPC service 名称自动推断 upstream 会路由错误。

现有精确注册同键覆盖，模板注册直接 append，但注释称重复覆盖。模板按注册顺序遍历；扩容前必须明确冲突和优先级。当前 Swagger 已经存在，不再重复建设第二套接口文档系统。

## 2. 目标与非目标

目标：普通接口由业务域维护契约；网关统一实施跨域治理；契约、实际路由、文档、权限目录可自动核对；新增接口不再复制手写绑定代码。

本轮不新增数据库，不增加路由配置管理后台，不允许在线任意修改 RPC 目标，不向公网开放 gRPC reflection，不把所有内部 RPC 自动映射为 HTTP。不迁移聊天业务规则、事务和数据归属判断到网关。

## 3. 三类接口及所有权

| 类型 | 处理方式 | 所有者 |
|---|---|---|
| 单服务普通 HTTP | Proto HTTP 契约生成适配器，装配到统一认证和治理链 | 对应业务域 |
| 聚合/编排 | 显式手写处理器，例如认证、组织选择、会话签发 | 网关/BFF 维护者与相关业务域共同审查 |
| 特殊协议 | WebSocket、文件上传下载、流式响应单独适配 | 协议模块维护者 |

业务域负责业务正确性；网关负责身份校验、策略入口、限流、超时、审计和追踪；后端继续校验资源可见性和操作权限。权限检查不能只依赖前端菜单或网关 URL。

## 4. 契约与元数据设计

推荐以 `google.api.http` 注解表达普通接口 HTTP 映射，用 gRPC-Gateway 在 todo 域验证生成。扩展安全元数据通过按域清单绑定稳定 operationId；不在 Proto、YAML、Go 中重复维护同一个 HTTP 路径。

建议结构（规划，不是已实现）：

```text
ppb-base/
  idl/*.proto                         # RPC 与显式 HTTP 注解
  api/policies/{todo,im,manage,...}.yaml # 身份、权限、负责人等补充信息
  server-gateway/internal/httpgen/     # 生成产物，不手改
  server-gateway/proxy/                # 现有治理与兼容适配
  server-gateway/internal/apicatalog/  # 描述符与策略连接、校验、导出
  cmd/api-catalog/                     # 不依赖真实上游的目录校验/导出工具
```

元数据至少包含：operationId、domain、owner、transport、RPC 完整方法、逻辑 upstream、身份类别、授权要求、超时、限流类别、审计类别、状态和废弃信息。方法/路径/请求响应描述符从 HTTP 注解或显式适配器获取。

身份类别与授权策略独立：anonymous/member/manage/device 等表示采用哪条认证链；self/app_perm/super_gov 维持当前管理授权语义。匿名必须显式声明；未知身份或遗漏策略拒绝构建/启动。不能将所有已登录成员强行套用 manage self 策略。

operationId 在迁移前后稳定。动态授权规则沿用 Go 中经过审查的 resolver，并由清单引用固定 resolver ID；YAML 不允许执行表达式或注入任意函数。缺失 resolver 拒绝启动。

特殊入口通过显式 RouteSpec 加入同一目录；静态资源、健康检查、文档页独立标记类别，明确是否属于公开业务 API。目录必须覆盖真实入口，不能只统计 Registry。

## 5. 路由匹配和注册校验

1. 同方法、同规范化路径重复注册：直接失败，不能静默覆盖或追加。
2. `/x/{a}` 与 `/x/{b}` 属于同结构冲突，拒绝。
3. 同方法且可匹配同一请求的模板，例如 `/x/{id}/detail` 与 `/x/fixed/{kind}`：本轮选择拒绝歧义，要求改路径；不能依赖注册顺序。
4. 精确路由优先于模板，保留现有公开语义；目录显示这种重叠并测试。不要因冲突检测误删有意保留的固定端点。
5. 校验空参数名、重复参数名、非法模板，以及参数对应请求字段是否存在。
6. 保持当前首尾斜杠等行为，先记录实际行为再决定是否单独变更；不要在治理提交中隐含改变。

目录建成后冻结为只读快照，运行期禁止新增路由。错误信息应包含两条冲突路由、域和来源位置。

## 6. 身份与兼容设计

当前 operatorRPC/operatorBindRPC 从可信上下文注入操作者。生成适配器必须实现相同行为：丢弃客户端伪造的身份字段与内部身份头，再从认证结果覆盖写入；后端服务继续验证调用方及资源权限。不得简单把用户传入的 operatorBizKey 转发到 RPC。

成员、管理员、设备身份不混用。保留内部调用凭证、request ID、取消和 deadline 传播。生成代理必须经真实 gRPC 客户端调用，不通过进程内直调绕过服务端拦截器。

必须对照当前实现逐项验证：

- HTTP 状态与 BaseResp/业务错误到现有信封的映射；包括 RPC 成功但业务失败。
- JSON 字段名、int64 字符串/数字、枚举、空值、省略字段、optional presence。
- 路径与查询同名时路径优先；GET 查询参数、布尔值和默认值。
- todo 当前 `overdueOnly` 同时接受 true/1；整数过滤参数存在自定义解析行为。生成器默认值不能直接替代现有规则。
- 请求体与路径主键冲突时主键取路径；可信操作者最终覆盖 body/query。
- 未认证、过期、已撤销、错身份类别、权限不足、上游超时和不可用。

## 7. 生成技术的决策门槛

优先做标准 gRPC-Gateway 试点，保留 Gin 为外围治理入口；生成 mux 只接管选定路由，旧处理器通过显式开关切换。两套处理器不能同时竞争同一路由，也不能对写请求执行双调用。

试点必须证明：身份注入可靠、原有信封与错误码兼容、既有中间件不被绕过、特殊解析只需有限兼容钩子、文档依然以 OpenAPI 3.0 为现有输出契约。

若为兼容现有行为必须大量修改生成代码或维护双路由真相，则暂停扩域，提交 ADR 比较“继续标准生成器适配”与“基于标准 HTTP 注解生成现有 Registry 调用”的复杂度。不得直接手改生成文件或无评估自建大型框架。

现有 OpenAPI 3.0 输出继续保留；不要未经转换验收就替换为生成器的 OpenAPI v2 输出。

## 8. 发布与规模边界

生成代码编译在统一网关中，新增接口仍需发布网关；本轮降低开发耦合，不承诺消除发布耦合。只有实际独立发布需求和运维能力成立后，才评估边缘入口按域转发到域级 HTTP 适配服务。

每域迁移有独立开关，回滚恢复旧处理器；无数据库迁移。生成产物可复现、依赖锁版本、接口契约变更通过 CI。不要将权限、限流和路由配置迁移为无审查的数据库热更新。
