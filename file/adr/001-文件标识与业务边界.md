# ADR-001 文件标识与业务边界
状态：v0.1设计采用；2026-10-27。

## fileuuid 还是 file_biz_key
“UUID”是值生成方式，“biz_key”是字段的职责，两者并不冲突。

|方案|优势|代价|结论|
|---|---|---|---|
|仅暴露雪花file_id|紧凑，内部JOIN方便|跨库耦合、JS大整数问题、结构信息外露|仅文件库内部关联|
|新增file_uuid并与file_biz_key并存|可统一UUID工具|两个等价外部标识、双重索引及转换、易混用|不采用|
|file_biz_key，值由UUID生成|沿用PPB规范，业务稳定，迁移存储不变|索引较BIGINT大，需精确比较|采用|
|内容hash作为文件标识|天然内容寻址|相同字节用途/权限/生命周期不同；未校验hash不可信任|仅物理去重，不对业务作身份|

新键示意：`file_7f6b6d51a9bc4fa18d00391025913cc2`。UUIDv4由服务端安全随机源生成，去连字符形成32位小写hex；列VARCHAR(64) utf8mb4_bin，唯一键兜底碰撞重试。API文件键视作opaque，不让调用方解析前缀以外语义。旧file_键保持原值，不要求32hex；仅校验长度/允许字符与查库，不能对历史键误用新正则。

- 文件库：`file.file_id → file_blob.file_blob_id` 用BIGINT；应用侧雪花发号，不使用自增。
- 业务库：`camera_work_files.file_biz_key`、`im_message_files.file_biz_key`。禁止跨库物理外键和JOIN；存量已用file_id的映射先批量回填键再切读。
- 传输：雪花ID均十进制字符串；file_biz_key原样字符串；字节数在当前后端上限小于JS安全整数时为JSON整数，扩大上限须升级契约。
- 业务数据不保存永久物理URL；签名URL只是短期能力凭证。
- 同文件跨应用不得直接绑定；业务授权复制产生目标应用的新逻辑键，物理复用仅在同dedup_scope且授权成立时允许。
- 删除后不复用file_biz_key；内容替换产生新键。重命名不改文件键、不改对象路径。

## 边界取舍
独立部署，不先新建仓库打断ppb-base依赖。文件服务移除IM/mail业务回调；业务经可信API领取访问凭证。file_console是单独应用，可拥有个人文件业务及BFF；不能借“原上传者”权限查看其他业务的附件。管理台查看元数据与查看内容分权。

不在文件层复制业务ACL；引用记录只证明已受保护/可用于授权的映射存在，服务客户端仍须核验每次资源访问。业务下架与文件技术隔离区分，平台全局下架优先于任何业务授权。
