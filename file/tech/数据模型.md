# 数据模型
物理列定义以[核心SQL](sql/schema.sql)及[媒体SQL](sql/media.sql)为准。所有字段至少两个单词，下划线连接；无物理外键、跨库JOIN；内部BIGINT、跨服务业务键。

## 核心15表
- `file_applications`：文件应用准入与技术政策。
- `file_storage_backends`：存储实例。
- `file_blob`：物理内容身份，无业务访问权。
- `file_blob_locations`：对象位置及固定版本。
- `file_quota`：技术容量聚合账。
- `file`：逻辑文件，跨服务用file_biz_key。
- `file_upload`：上传会话与崩溃恢复。
- `file_upload_parts`：分片状态缓存，后端ListParts为真源。
- `file_refs`：业务保护与乱序墓碑，不存业务ACL。
- `file_quota_events`：容量幂等流水，与余额同事务。
- `file_tasks`：后台任务与租约。
- `file_orphans`：按对象复用状态行，历史操作进审计。
- `file_audit_logs`：文件治理审计，不记录签名URL。
- `event_outbox`：本库可靠事件外寄；可适配现有共享outbox。
- `event_inbox`：可靠事件防重放。

## 关系
file_applications引用IAM应用，只缓存准入配置，IAM是身份真源。file→blob→locations→storage_backend；file→quota。上传会话预留quota，完成回填result_file_id；parts仅作进度缓存。refs指向file并保留target_file_biz_key，早到release可先落无file_id墓碑，非released必须有file_id。outbox/inbox与本库状态同事务。

业务库示例：camera_work_files(camera_work_file_id, camera_work_file_biz_key, camera_work_id, file_biz_key, file_role, sort_number, create_time, update_time)。同一业务记录可多文件，用唯一键(camera_work_id,file_role,sort_number)，映射删除/唯一重用政策由业务决定；文件服务不强迫全业务采用同一个映射表。

## 媒体4表
media_assets存探测属性，media_jobs存输入/方案/租约，media_outputs关联独立file或package，media_packages管理HLS/DASH包。输出要么文件要么包；任务幂等request_key在同应用内唯一，相同key不同input/profile/version返回409。包内切片不成为业务可见file。P1包的保护引用属于媒体服务，业务prepare/commit/recycle/release与file引用采用同样终态/乱序原则；其对象容量、保护验证和GC由媒体端口实现，不得用file_refs的file_id冒充包ID。

## 计数与时间
blob.logical_ref_count = 非purged且确实关联该blob的file行数；业务refs不直接计入，只阻止这些file被purge。生成图片/MP4也是file，因此计数统一。
used=所有已提交未清除逻辑文件及媒体包实际字节；recycled是used子集，reserved另计。去重节省物理容量不减少每个逻辑文件的计费，若改为物理计费需另立ADR。
zero_ref_time专供GC，update_time不承担归零语义；unbound_expire_time是未绑定上传保护，purge_after_time是个人回收站期限。prepared未知不能按任意时间到期自动释放。file.deleted_flag与recycled/purge_pending/purged保持一致；恢复ready时清deleted_time、purge_after_time，不能立即再次回收。
逻辑file和blob删除均保留墓碑直到归档，以防旧事件、旧业务键重放；物理字节不可恢复后返回410，不伪报恢复成功。
