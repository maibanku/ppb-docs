# 业务接入与跨服务一致性
## 业务映射
chat使用消息级im_message_files；camera使用camera_work_files；wardrobe使用wardrobe_item_files；mail使用mail_attachment_files。保存本库记录ID、file_biz_key、用途、排序及可信展示快照。文件核心不保存会话成员、衣服类别、作品文案。跨库只用接口，不JOIN。
用户头像可继续保留user_file作为业务映射，但必须确认文件来源、应用、归属、就绪、允许类型和真实大小；不能接受任意file_字符串与客户端大小直接落库。

## 上传与绑定
1. 业务鉴权、权益检查，可信调用创建上传会话；文件服务预留容量。
2. 客户端直传；文件服务核验并生成ready资源，未绑定文件72h保护。
3. 业务请求prepare引用：声明reference_key、file_biz_key、reference_version=1。文件验证同应用的上传认领权或显式复制授权，并写prepared，prepared立即阻止GC；返回reference_biz_key。
4. 业务本库事务写映射+outbox，业务记录可先attachment_pending。
5. relay提交commit引用，文件服务幂等转active；回执后业务标记附件可用。业务txn失败则通过release补偿。
6. prepared失联进入对账，调用可信业务状态查询判定已提交/已回滚/未知。未知冻结清理并告警；不能TTL自动删后再接受迟到commit。长时间冻结是可观测异常，有限流与人工处置。
7. 普通未prepare上传保护到期且无任何保护后可回收；超期才发起prepare返回过期/冲突，业务不能假设曾上传永久可绑定。

prepare与GC锁定相同file/blob，状态不允许则409。已purged文件不能恢复。业务本库事务与文件事务不称作原子事务。

## 版本与事件
同一reference_key永久指向同一个file_biz_key，不重用给新文件；换图先准备新reference_key再更新业务映射，最后释放旧引用。
事件含event_biz_key、application_biz_key、reference_key、reference_version、event_type、occur_time；event_key防重复，reference_version防乱序。release若早于prepare到达，仍写带file与版本的released墓碑；迟到较低版本prepare/commit不能复活。相同版本且payload不同409。
业务回收站用recycle保护状态，仍阻止GC；恢复递增版本转active；最终release是终态，不允许更高版本复活，恢复已终态引用需新key并重新确认文件可绑定。
消费者inbox与状态变更同事务；outbox投递至少一次；业务状态接口和对账均需服务身份，不开放任意URL回调避免SSRF。

## 下载与跨应用复制
客户端请求业务记录→业务判ACL→提供该记录的active reference_key申请访问。文件服务不回调业务判断成员，而验证请求来源、引用与文件状态。
相同用户在camera拥有文件不意味着能在chat直接绑定该键。复制操作必须源业务完成授权，通过文件平台受控内部复制形成目标应用新file_biz_key；首版默认拒绝跨应用绑定/签发，不提供浏览器自由复制源键。

## 删除
业务回收站保留引用；彻底删除事务提交outbox释放引用。个人工作台只有file_console作用域可操作recycle/restore/purge。purge是异步请求：有prepared/active/recycle/processing引用则409，任务最终二次验证。任一共享blob还有未清除file行则不物理删。
对账分类：上传未绑定、prepared失联、业务有映射文件无引用、文件引用有记录业务已删除、blob物理缺失。缺失不得自动“恢复成功”。
