# 邮件域 PRD

> v0.4 · 2026-11-26。目标态设计。实现从 2026-11-25 起在 ppb-mail 和几个平台仓库的分支上进行，没有合并，也不代表任何接口已上线；进度见 [实施进度](implementation/PROGRESS.md)。v0.1 的现状文档仍有效，见“现状”一节。

[返回域导航](README.md)

## 1. 定位

为企业自建一套完整的邮件系统：有自己的邮件域名，能在公网上收发邮件，员工用 Outlook、Foxmail、系统邮件等标准客户端收发，平台也提供 HTTP 接口供后续自有客户端和其他业务使用。

系统分两部分：

| 部分 | 说明 | 状态 |
|---|---|---|
| 邮箱系统 | 邮件服务器核心加自研控制面，含成员 HTTP 接口和管理端 | 本 PRD 的目标态，待建 |
| 系统通知邮件 | IAM 的注册、找回密码、换绑邮箱验证码邮件 | 运行中，有缺口 |

系统通知邮件自己的需求在本文件第 9 节。两者的关系是我的建议，需要你确认：当前不合并，验证码邮件继续经外部 SMTP 中继发出，缺口单独先修；自建邮件服务器稳定运行之后再评估是否切过来。理由见 [ADR-006](adr/006-通知邮件通道.md)。

## 2. 已拍板的方向

2026-11-24 拍板，记录在 [ADR-001](adr/001-邮件域范围与现状.md)：

| 事项 | 结论 |
|---|---|
| 是否重建邮箱 | 重建，作为完整邮箱系统 |
| 收发范围 | 自建公网收发，不接第三方邮件服务 |
| 服务器核心 | 成熟组件 Postfix、Dovecot、Rspamd 加自研控制面 |
| 成员收发方式 | 标准邮件客户端和 HTTP 接口都支持 |
| 使用对象 | 企业全员，数百到数千人 |
| 本阶段客户端 | 原定只做后端和管理端；2026-11-25 增加成员网页客户端，放在 ppb-mail/ui，布局参照设计稿 |
| 部署条件 | 已有公网服务器、固定 IP 和域名 |

## 3. 目标与非目标

目标：

- 员工用标准邮件客户端就能与公网上任何邮箱互通，收信、发信、退信行为与商业企业邮箱一致。
- 邮箱账号与 IAM 用户一一对应，人员入职、停用、离职时邮箱状态自动跟随。
- 管理员能在管理端管理域名、邮箱、别名、黑名单、出站限额、队列，并查看投递和登录日志。
- 外发邮件带 DKIM 签名，入站邮件做 SPF、DKIM、DMARC 校验和垃圾评分。
- 提供 HTTP 接口，覆盖收件箱、写信、读信、附件、搜索和设置。

非目标：

- 不做成员用的桌面或移动端邮箱界面。网页端已在 2026-11-25 纳入范围。
- 不做多租户或对外运营，一个部署只服务一家企业。
- 不做邮件归档、电子取证、邮件审批、DLP 等合规产品功能。
- 首期不做高可用，单节点部署。
- 不迁移任何历史邮件数据；已下线的站内邮箱没有需要迁移的数据。

## 4. 用户与场景

| 角色 | 场景 |
|---|---|
| 员工 | 用 Outlook、Foxmail、系统邮件等客户端收发；设置自动回复、转发、过滤规则；修改邮箱密码 |
| 员工 | 通过 HTTP 接口读写自己的邮箱（供后续自有客户端或其他业务） |
| 邮件管理员 | 添加域名并完成 DNS 配置；开通、停用邮箱；重置密码；调整配额和外发权限 |
| 邮件管理员 | 管理别名、转发、黑名单、出站限额；处理积压邮件；查投递和登录日志 |
| 邮件管理员 | 查看系统状态：队列、磁盘、各组件健康、证书到期 |
| 运维 | 部署、备份、恢复、监控、升级 |
| 平台管理员 | 给角色分配邮件管理权限 |

## 5. 阶段

| 阶段 | 内容 | 出口 |
|---|---|---|
| M0 | 修复系统通知邮件的缺口，独立于邮箱系统 | 投递超时、投递通道标识、模板单一来源、管理页类型筛选有自动化或走查证据 |
| M1 | 工程骨架：仓库、契约、服务骨架、配置检查、迁移、CI、部署编排骨架 | 新仓能独立构建和测试，`-check-config` 正负控通过 |
| M2 | 收发主干：域名、DKIM、账号、密码、入站、出站、IMAP、SMTP 提交、TLS、反垃圾接入 | 公网真实环境里，标准客户端与外部邮箱双向收发成功 |
| M3 | 成员 HTTP 接口和网页客户端 | HTTP 接口全部操作在测试环境通过；与标准客户端看到的是同一份邮件；网页客户端覆盖设计稿的 16 屏，类型检查、测试和构建通过 |
| M4 | 账号同步与管理端 | IAM 状态自动同步到邮箱；管理端全部页面可用并有权限控制 |
| M5 | 加固与运维 | 备份恢复演练、监控告警、规模压测、运维手册完成；旧残留清理完毕 |

阶段之间有依赖：M2 依赖 M1，M3 和 M4 依赖 M2，M5 依赖 M4。M0 可以随时开始。详见 [实施路线](implementation/README.md)。

## 8. 非功能需求

| 编号 | 要求 |
|---|---|
| NFR-M01 | 标准客户端收发对外可用率不低于 99.5%（按月），不含计划内维护 |
| NFR-M02 | 入站邮件从收到到进入收件箱，p95 不超过 10 秒；被灰名单延迟的除外 |
| NFR-M03 | 出站邮件在收件方正常的情况下，p95 不超过 30 秒完成投递 |
| NFR-M04 | HTTP 接口读操作 p95 不超过 500 毫秒（搜索不超过 2 秒），写操作 p95 不超过 1 秒 |
| NFR-M05 | 控制面服务不可用时，已登录用户的标准客户端收发不受影响；新登录和自动回复、过滤设置变更受影响 |
| NFR-M06 | 数据库不可用时入站收信暂存队列并延迟投递，不丢信；恢复后自动续投 |
| NFR-M07 | 备份每日一次；单账号恢复在 1 小时内完成，全量恢复在 8 小时内完成；备份保留 14 天 |
| NFR-M08 | 所有管理写操作记审计，包含操作者、时间、对象、变更前后值 |
| NFR-M09 | 邮件存储、数据库、DKIM 私钥、TLS 私钥不出现在日志和普通备份目录之外的任何地方 |
| NFR-M10 | 配置错误时服务拒绝启动，并给出不含秘密的错误信息 |
| NFR-M11 | 在 3000 用户、日均每用户 50 封的规模下，队列不持续积压，磁盘占用可预估 |

## 9. 系统通知邮件的需求基线

这部分是运行中的代码，2026-11-24 对照 ppb-iam main@86f19e8 核对。73 条规则的逐条状态见 [系统通知邮件](pr/01-系统通知邮件.md)，现状设计见 [投递设计](tech/01-系统通知邮件投递设计.md)。

### 9.1 目标与非目标

目标：

- 验证码邮件的每一条规则都能在文档里找到出处，并有对应验收。
- 投递通道的状态对管理员可见：是否真发、是否失败、失败原因。
- 记录里的内容和实际发出去的邮件一致。

非目标：

- 不定义验证码挑战本身的生成、存储和校验，那属于 IAM 账号域。
- M0 不把验证码邮件迁到自建的邮件服务器，见 [ADR-006](adr/006-通知邮件通道.md)。
- M0 不做异步投递、重试、退信、来源限流和查看审计。

### 9.2 角色与场景

| 角色 | 场景 |
|---|---|
| 未注册的访客 | 输入邮箱，获取注册验证码 |
| 忘记密码的用户 | 输入邮箱，获取找回密码验证码 |
| 已登录的用户 | 校验当前密码后，向新邮箱获取换绑验证码 |
| 平台管理员 | 在管理端查看推送记录，按收件人、类型、通道、时间筛选，分辨真发和只写了日志 |
| 运维 | 配置 SMTP 中继和口令，确认生产环境是真投递 |

### 9.5 依赖与边界

| 依赖 | 说明 |
|---|---|
| IAM 账号域 | 挑战的生成、限流计数、存储、校验、消费 |
| SMTP 中继 | 生产投递通道，587 端口，STARTTLS |
| ppb_iam 库 | 挑战表、投递记录表 |
| 网关 | 路由 /api/v1/manage/email-log 到 IAM，并做权限前判 |
| 管理端 | 推送记录页，在 chat-manage-web 里 |

边界：

- 只记录 IAM 出站的验证码类邮件，不跨库聚合其他域的邮件记录。
- IM 的组织邀请是令牌制，仓内没有邀请函邮件的投递，是否需要见 MAIL-10。

### 9.6 开放问题

这些都不在 M0，需要另行决定：

1. 投递是否改为异步，是否重试。
2. 中继的异步退信由谁接收。
3. 是否增加按来源的发码限流。
4. 查看推送记录是否记审计。
5. 验证码的时效、尝试次数、限流数值何时定案，属于 IAM 的架构决策。
6. 换绑时通知旧邮箱、邮箱验证码登录、第三方登录后绑定邮箱、组织邀请通知，是否纳入范围。

## 11. 待确认

以下几项我给了建议值，需要你确认或修改：

1. **自动开通范围**：建议指定组织的成员自动开通。另外两个选项是管理员手动开通，或所有 IAM 用户自动开通。
2. **管理员能否查看成员邮件内容**：建议不能，管理员只看得到元数据。
3. **邮箱地址规则**：建议新邮箱的地址先由系统用用户编码生成，用户可改成自定义账号名，限一次。
4. **第 7 节的数值**。
5. **部署信息**：邮件域名、主机名、服务器 IP，在 M2 开始前提供。
6. **系统通知邮件**：建议留在 IAM，继续走外部 SMTP 中继，不并入自建服务器；缺口单独先修。其中两项原来待决策的规则我按建议值设计并实现了（在分支上，未合并）：投递记录保留 180 天；生产环境开着日志投递时拒绝启动。
7. **附件大小**：HTTP 接口单个附件 25 MB、每封合计 35 MB。原因是附件编码后会膨胀约三分之一，这样整封邮件编码后仍在 50 MB 以内。原来的写法是单个 40 MB、合计 50 MB，和单封 50 MB 的上限冲突。

开发中发现、需要你定的几项（2026-11-25 补）：

8. **转发到外部地址时要不要改写信封发件人**：设计写的是开启，由 Rspamd 改写；实测 Rspamd 没有这个模块。现在是没有改写。不改写时，原发件域只靠 SPF 的转发邮件可能在收件方被拒。建议先这样上线，看退信情况再决定要不要另加一个改写组件（如 postsrsd）。
9. **超级管理员的邮件管理权限**：`pr/06` 的 G16-3 写的是超管默认拥有全部权限。平台的口径是超管也要持有角色，才能通过业务服务的权限复检。建议把 G16-3 改成「部署时给超管分配内置角色 mail_admin」，不改平台。
10. **停用的邮箱被拒时的状态码**：验收标准写的是 550，实际是 554 5.7.1，提示语里带 Mailbox disabled。Postfix 的访问表对 REJECT 固定回 554。建议验收标准改成 554。
11. **告警的接收通道**：`pr/07` 的 O03-4 写的是接平台现有的监控方式，平台现在没有监控栈。控制面做成通用的 HTTP 通知：配一个地址就发，不配只记日志。等平台有了监控再对接。
12. **对账里的「IAM 用户注销」**：IAM 现在没有把用户置为注销的写口，这条规则目前不会触发。规则保留，等 IAM 支持注销后再验证。
13. **「按组织开通」和自动开通范围里的「指定组织的成员」**：对着真实的平台核过，当前做不了。IM 的成员列表是管理接口，后台的对账任务调它会被拒；聊天产品转向 C 端之后组织管理面也退役了。现在默认值的行为等于「手动开通」（组织列表为空时不自动开通）。建议把这两个功能从范围里拿掉，自动开通范围只留「手动开通」和「全部 IAM 用户」，默认值改成「手动开通」。
14. **「设置初始密码成功后通知 IAM 登录邮箱」现在发不出去**：用户的登录邮箱只能从 IAM 的 `InspectAccount` 取，那个接口只允许带管理员身份的调用，而设置初始密码的是成员本人。要么接受这条通知先不发，要么让 IAM 提供一个只凭内部凭据、按用户标识取登录邮箱的接口。
15. **管理端接口的权限在哪一个应用域下判**：经 IAM 业务桥来的请求（管理端界面走的那条路）按 mail 应用判，没有问题。带管理端登录凭据直接调接口的那条路，契约里写的是按 chat 应用判 `mail.*` 的权限码（平台的权限守卫当时只认 base、chat、camera 三个应用）。要走通这条路，IAM 里要把这 19 个权限码在 chat 应用下也登记并授给管理员；或者等平台的权限守卫认 mail 应用之后，把契约改成按 mail 应用判。
16. **「设置初始密码要求近期认证」（A16-2）现在只是退而求其次**：成员的登录态里没有「什么时候认证的」，IAM 查会话的接口也不返回，所以控制面只能记「这个登录态第一次被邮件服务见到的时间」，5 分钟内算数。有两个漏洞：控制面重启后的 5 分钟里，所有活着的登录态都被当成刚认证过；很久以前登录、从没访问过邮件服务的登录态，第一次来也算。可靠的判法要平台补：让 IAM 的会话里记认证时间并返回给服务间调用。要不要补，或者接受现在这个程度，需要你定。

其余设计取舍见各 ADR。
