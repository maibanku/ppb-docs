# 实施路线

> v0.2 草案；设计尚未评审，代码一行未写。设计评审通过、待确认项有答案之后，才生成逐任务的实施计划并开始执行。执行入口见 [Claude Code 执行提示词](CLAUDE_CODE_PROMPT.md)，实际结果写在 [实施进度](PROGRESS.md)。

[需求基线](../PRD.md) · [域导航](../README.md)

## 1. 推进方式

1. **设计评审。** 你审这套文档，答复 [PRD](../PRD.md) 第 11 节的待确认项。评审意见改回文档。
2. **按阶段生成逐任务计划。** 一个阶段一份计划，放在本目录的 plans 子目录，例如 plans/M2-收发主干.md。计划里每个任务有要改的文件、先写的失败测试、验证命令。计划也过你这一关。
3. **执行。** 按计划一个任务一个任务做：先写失败的测试，再实现，再跑检查，再提交。进度和证据写进 PROGRESS.md。
4. **过验收门。** 阶段结束时对照 [验收标准](../ac/02-邮箱系统验收标准.md) 的验收门，逐条填状态。门不过不进入下一个阶段。

分阶段生成计划而不是一次生成全部，是因为 M1 的技术核对会改变后面几个阶段的做法。M2 在公网上的实测也会带来调整。

## 2. 阶段总览

| 阶段 | 目标 | 依赖 | 出口 | 相对工作量 |
|---|---|---|---|---|
| M0 通知邮件缺口 | 把验证码邮件的缺口修掉 | 无，随时可以开始 | G2、G3 的待补用例补上；G7、G8 有证据 | 小 |
| M1 工程骨架 | 新仓库、契约、服务骨架、镜像和编排、技术核对 | 无 | MG-0 到 MG-3 | 中 |
| M2 收发主干 | 公网上用标准客户端和外部邮箱双向收发 | M1；域名、服务器、DNS 的控制权 | MG-4 | 大 |
| M3 成员接口 | HTTP 接口全部可用，和标准客户端看到同一份数据 | M2；网关的流式车道 | MG-5 | 大 |
| M4 账号同步与管理端 | IAM 状态自动同步；管理端全部页面 | M2；IAM 的新增接口、门户的插件接入 | MG-6 | 大 |
| M5 加固与运维 | 备份、监控、压测、手册、残留清理 | M4 | MG-7 | 中 |

M3 和 M4 互不依赖，可以先做 M4 再做 M3，也可以并行。并行的话两边改同一个仓库，要用各自的分支。

工作量只是相对大小。实际耗时主要花在公网实测、DNS 生效的等待、跨仓库的评审上，不在写代码上。

## 3. 各阶段做什么

每个阶段列的是功能层面的任务块和它们的先后。文件级的任务划分留到逐任务计划里。

### 3.1 M0 通知邮件缺口

完全按 [缺口修复设计](../tech/11-通知邮件缺口修复设计.md) 做，九项修复、九个提交、两个仓库。开始前只需要确认一件事：[PRD](../PRD.md) 第 11 节的第 6 项。

### 3.2 M1 工程骨架

| 任务块 | 内容 | 顺序 |
|---|---|---|
| 建仓 | 新建 ppb-mail。初始化 README、目录骨架、CI。先确认工作区里已有的 ppb-mail/ui 是什么 | 1 |
| 契约骨架 | contracts-mail：buf 配置、公共消息的引入方式、生成代码和 Kitex 桩的模块划分、Go 访问器。先放最小的一组消息，之后每个阶段往里加 | 2 |
| 服务骨架 | cmd/server 入口；配置加载和 -check-config；启动装配；/ping、/healthz、/metrics；数据库连接；迁移入口；优雅关闭；日志 | 3 |
| 数据库迁移 | 把 schema.sql 拆成第一个迁移脚本；迁移在空库上可执行、可回滚 | 3 |
| 运维代理骨架 | mailops 的监听、请求响应格式、白名单机制、两个命令：status、reload | 4 |
| 镜像和编排 | mailcore 镜像的构建；编排文件；配置模板的目录结构；一份开发用的编排 | 4 |
| 平台接入 | IAM 客户端、IM 客户端的出站配置；成员登录态的校验器；ppb-base 的路由清单启用 mail | 5 |
| 技术核对 | 把各技术设计末尾“实现时要核对的事项”逐项核对完，结论写回文档 | 贯穿 |

技术核对是 M1 最重要的产出。它决定了 M2 的配置怎么写。核对的办法是在开发用的编排里把组件跑起来，动手试。

| 仓库 | 改动 | 阶段 |

| ppb-base | 路由清单启用 mail；start-all 启动控制面；平台门户注册插件；删除 mail.yaml；文档改口径 | M1、M4、M5 |

## 6. 风险

| 风险 | 影响 | 怎么应对 |
|---|---|---|
| 新服务器的送达信誉 | 发出去的邮件进垃圾箱或被拒 | 上线前把 DNS、证书、反向解析一次做对；小范围试运行；验收里有专门的三项校验检查 |
| 技术核对发现某个设计点不成立 | M2 的配置或结构要调整 | M1 把核对做完再往下走。各设计末尾的清单就是为此准备的 |
| IMAP 往返拖慢 HTTP 接口 | 达不到 NFR-M04 | M3 一开始就做技术验证和性能测量，不等到最后 |
| 公网暴露的攻击面 | 被当作中继、被爆破、被利用发垃圾 | 开放中继测试是 M2 的必过项；登录失败防护；出站限额；监控里的认证攻击告警 |
| 自动开通的邮箱设不了初始密码 | M4 的自动开通在成员界面上线前不完整 | 管理员可以重置密码作为过渡；提前告诉你这个限制 |
| 范围大，一个阶段拖得过长 | 迟迟看不到可用的东西 | 阶段是纵向切的：M2 结束时就有一套能用的邮箱 |
| 旧表归档和新库同名 | 迁移撞上旧表 | 上线前检查清单里确认旧表已归档 |
