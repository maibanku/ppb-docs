## 任务块（按顺序做，每块做完提交一次）

### 1. 域名（`internal/maildomain/`）

- 增、删、改查，默认域，域状态。删域时域下还有邮箱、别名或保留地址不能删（`mailerr.ErrDomainNotEmpty`，D01-5）；能删时在同一事务里删掉它的 DKIM 密钥行和保留地址行，提交之后再删磁盘上的私钥文件，文件删不掉只告警（`tech/08` 第 5.1 节）。第一个域自动成为默认域；默认域至多一个，切换照 `tech/08` 第 9.2 节。
- **DKIM**：RSA 2048 位私钥；选择器叫 `s` 加年月（如 `s202611`），同月多次轮换追加序号；私钥写成 PEM（不带口令），放在 `<dkim_dir>/<域名>/<选择器>.key`，表里的 `dkim_key_path` 记相对密钥目录的路径（`<域名>/<选择器>.key`）。**文件权限 0440、各级目录 0755**——邮件核心那边实测：读它的是 Rspamd 的工作进程（不是 root），靠「组可读」才读得到（见 `ppb-mail-ws/ws4-infra/deploy/docs/control-plane-contract.md` 第 3.7 节，只读）；别写成 0444。运行用户不是 5000、设不了属主时记告警，测试环境不要求。由私钥算出 DNS TXT 记录值存库，格式 `v=DKIM1; k=rsa; p=<base64>`。域名和选择器只允许各自的合法字符（它们会被写进 Rspamd 的配置文件）。添加域时给这个域插两条保留地址记录（指向请求里给的邮箱）。**先写文件再写库**（`tech/07` 第 9.1 节的理由）；库写失败时留下孤立的私钥文件，由每日维护清理。私钥不进库、不进日志、不进审计、不进错误信息——有测试扫过这些输出。
- 轮换：生成新选择器和新密钥，新密钥标成当前签名用的，旧的保留；删旧选择器。
- 域、选择器变了之后调 `ports.go` 里的 `DKIMRenderer.RenderDKIM`。它是空指针（配置渲染还没做）时跳过，不报错，记一条告警日志。
- **主机名登记**：接缝的 `Startup` 钩子里把配置里的对外主机名和公网地址写进登记表；和以前的值不同时 `GetEndpoint` 的 `changed` 为真，并异步触发一次全局 DNS 校验。
- **DNS 校验**：六项（MX、SPF、DKIM、DMARC、主机名解析、反向解析），通过条件照 `tech/07` 第 9.4 节的表。用 `github.com/miekg/dns` 直接向配置里的公共递归服务器查；单项超时 10 秒，整轮不超过 60 秒。结果三种取值（通过、失败、未检测），每项带一句不含敏感信息的说明。DKIM 那一项要把拆成多段的 TXT 拼起来，再把公钥和本地密钥比对。测试起一个内存的 DNS 服务器（`miekg/dns` 自带 server）逐项给应答。
- 每日维护里登记一轮「DNS 校验」（`CheckAll`，它同时满足 `mailstatus.DomainDNSChecker`，发布能力 `deps.X.DomainDNS`）。
- 域的服务对象还要满足成员邮箱那一轮定义的接口 `mailnotify.DomainSource`（成员邮箱的接缝从 `deps.X.DomainDNS` 上按类型取；那个包现在还不在你的分支里，照签名写，集成时自然对上）：
  `DefaultDomain(ctx context.Context) (string, error)`——默认域的域名。控制面自己发出的三种通知邮件（转发确认信、初始密码设置成功的通知、容量预警）的 From 都用它拼 postmaster 地址；没有默认域时返回业务错误，调用方落 MAIL-3003。
- 域的服务对象还要满足投递与运维那一轮定义的另一个接口（它从 `deps.X.Accounts` 或 `deps.X.DomainDNS` 上按类型取）：`mailstatus.DNSSummarySource`，方法是
  `DNSSummary(ctx context.Context) (*mailstatus.DNSSummary, error)`——读域表最近一次的校验结果，给系统状态页用。类型的定义在
  `/Users/pipi-ban/Desktop/code/vscode/ppb-mail-ws/ws3-be-ops/service-mail/internal/mailstatus/sources.go`（只读；合并 main 之后如果这个包已经在你的分支里就直接用）。返回各域的汇总（标识、名称、状态 0 未校验 / 1 全部通过 / 2 有未通过、未通过项的名称、校验时间）和全局检查项（主机名解析、反向解析）的结果。没接上时系统状态里这一组是空的。

### 6.1 转发确认的后两步（成员邮箱那一轮定义的）

成员邮箱那一轮给 `mailbox` 加了一个窄接口 `ForwardVerifier`（那个包现在还不在你的分支里，照签名写）。你的账号服务对象——就是发布到 `deps.X.Accounts` 的那一个——要有这两个方法，成员邮箱的接缝经类型断言取：

```go
// 给已有的转发设置重新生成一次性令牌，把令牌的明文和过期时间返回给调用方（确认信由调用方发）。
// 已经验证过的、或者还没有设置转发的，返回业务错误。
ResendForwardVerification(ctx context.Context, accountID uint64) (token string, expiresAt time.Time, err error)
// 按令牌把转发标记为已验证、清掉令牌。令牌不对、过期、已经用过都返回业务错误（400，原因在文案里）。
VerifyForward(ctx context.Context, token string) error
```

- 第一轮的 `SetForward` 已经负责生成令牌、存哈希和过期时间；这里的「重新生成」复用它，旧的令牌作废。
- `VerifyForward` 对应的 HTTP 接口是**匿名的**（谁拿着确认信里的链接都能来点），所以错误的文案里不能带邮箱地址，也不能让人从文案里试出「哪个邮箱设了转发」；令牌要够长、只能用一次、48 小时有效。
- 管理员关闭了用户自助转发（全局设置 `member_forward_enabled`）时两个方法都返回 MAIL-2005。
- 这两个方法各有测试：重新生成后旧令牌不认；令牌不对、过期、用过第二次都失败且文案里没有地址。
