## 目标

到今天为止，控制面从来没有和邮件核心一起跑过：邮件核心那边的开发编排里控制面是一个替身容器，控制面这边的验证要么是单元测试，要么是一次性的容器。这一步要有一份**在本机把真实的控制面镜像和邮件核心一起拉起来**的编排，并且证明下面这几件事：

1. 控制面在一个空库上完成迁移、渲染出全部配置文件、开始监听；`/ping` 回 200，`/healthz` 回 200 且每一项都是 ok。
2. 邮件核心的入口脚本接受控制面渲染的文件，Postfix 和 Dovecot 都起来并且健康。
3. 控制面的日志里不出现任何口令、连接串、私钥。
4. `docker compose stop service-mail` 再 `start`，控制面能原样起来（重启动不重复迁移、不弄坏已渲染的文件，主账号口令文件被 Dovecot 继续接受）。

## 要做的东西

### 1. 一份联调用的编排 `deploy/compose/docker-compose.e2e.yml`

以开发编排为底，区别只有这些：

- **项目名、网段、宿主机端口都和开发编排错开**，两套可以同时在本机跑。建议：项目名 `ppbmail-e2e`，网段 `172.31.0.0/24`，控制面的固定地址 `172.31.0.10`；宿主机端口只绑回环地址，用 2535、1475、1597、1153、1994（邮件协议）、13307（MySQL）、19118（控制面 HTTP）、19108（控制面 gRPC）。策略服务的端口不发布到宿主机。
- **去掉控制面的替身**，换成真实的控制面：服务名 `service-mail`，镜像 `ppb-mail/service-mail:<标签>`，占上面那个固定地址，`user: "5000:5000"`，环境变量照契约第 2 节（七个秘密加 `PPB_INTERNAL_RPC_TOKEN`）。
- **共享的目录改成控制面可写、别的服务只读**，这是和开发编排最大的不同（开发编排里这些文件是脚本渲染好、大家只读的）：
  - `mail-config`：控制面写，邮件核心读；
  - `secrets/master`、`secrets/dkim`：控制面写，邮件核心和 Rspamd 读；`secrets/tls`：证书脚本写（宿主机上），两边都只读；
  - `rspamd-local`：控制面写，Rspamd 读。开发环境专用的 `settings.conf`（按 `X-Dev-Action` 定处置）还要在，脚本准备的时候写进去；**控制面不要动它**——顺便核实一下控制面的全量渲染不会删目录里它不认识的文件。
  - 可以用宿主机目录（放在 `deploy/compose/e2e/.state/` 下，加进 `.gitignore`），也可以用数据卷加一个初始化任务，照正式编排的做法。选一种，写明理由。
- **数据库是空库**：控制面启动时自己迁移。所以 MySQL 的初始化只建库和三个账号（复用 `deploy/compose/dev/mysql/02-accounts.sql.tmpl`），**不导入** `schema.sql`，也不导入开发用的种子数据（那些行绕过了控制面，后面几步要在控制面自己的迁移结果上做业务）。
- `rspamd` 依赖 `service-mail` 健康（控制面渲染完才启动它）。
- 出站邮件照旧交给 `mailsink`，不进互联网。证书是自签的（复用 `gen-dev-certs.sh`）。
- IAM 和 IM 先不可达：配置里给一个连不上的地址（比如 `127.0.0.1:1`）。控制面的出站客户端是惰性建连，对端不可达不影响启动；这一步不做平台的登录和权限，后面几步再接替身。

### 2. 一个脚本 `deploy/scripts/e2e.sh`

子命令：`prepare`（生成口令和证书、渲染账号的 SQL、渲染控制面的配置文件、从本分支构建控制面镜像和邮件核心镜像）、`up`（拉起并等全部健康）、`ps`、`logs <服务>`、`stop`、`start`、`down`（连数据卷一起删）。照 `dev-*.sh` 的写法（`set -euo pipefail`，变量后面紧跟全角字符时写 `${变量}`——macOS 的 bash 3.2 会把多字节字符并进变量名）。

口令是随机生成的，只落在 `.state/` 里（不入库），脚本和文档都不回显它们。要给人手工连库时，脚本另给一个 `env` 子命令把环境变量打到标准输出，供 `eval` 用。

控制面的配置文件从 `service-mail/env/mail-dev.yaml` 改出来（模板放在 `deploy/compose/e2e/` 下）：地址按联调网络改，`imap_insecure_skip_verify: true`（自签证书，开发环境才允许），`master_allow_nets` 是控制面的固定地址加 `/32`。

## 要验证的（逐条给证据）

1. **迁移**：MySQL 是空库，控制面起来之后库里有 24 张业务表加版本表、8 个视图（进容器用 `mail_ctrl` 查 `information_schema`）。**迁移用的账号是控制面自己**，不走别的路。
2. **渲染**：`mail-config/` 下有契约第 3 节列的那几个文件、`secrets/master/users` 有主账号那一行、`rspamd-local/` 下有 `actions.conf`、`dkim_signing.conf`、`whitelist.inc`；权限位和契约一致（0640、0400、0644；属主在 Docker Desktop 上不作数，写明）。
3. **控制面**：`curl http://127.0.0.1:19118/ping` 回 200；`/healthz` 回 200，响应里每一项都是 ok，把响应原文记下来；`/metrics` 能抓到。
4. **邮件核心**：容器健康；在容器里 `postfix status` 两个进程都在；从宿主机连 `127.0.0.1:2535` 能拿到 Postfix 的问候，连 `1993` 是 TLS。 Dovecot 用控制面写的主账号口令文件：在邮件核心的容器里用 `doveadm auth test '<邮箱>*<主账号用户名>' <主账号口令>` 验一次（库里现在还没有邮箱账号，所以验「主账号这一步过了、卡在邮箱不存在」还是「直接认证失败」，要看清楚是哪一种并解释；想验完整的一步，可以等后面几步有了账号再回来补）。
5. **日志里没有秘密**：把 `service-mail` 容器从启动到稳定的全部日志存下来，拿 `.state` 里的每个口令的值、连接串的值去搜，一个都不许出现（脚本里做这一步，不要把口令贴到终端）。
6. **重启**：`e2e.sh stop service-mail` 再 `start`（或者 `docker compose restart`），控制面回到健康，`mail-config` 下的文件内容不变（重启前后各算一遍摘要比对），`master/users` 的那一行不变。

## 发现问题时

控制面这一侧的问题（渲染少了文件、启动顺序、健康检查、日志带秘密、重启后行为不对）**不要自己改 `service-mail/`**：把现象、复现命令、你判断的原因写进报告，由负责人改。编排和脚本的问题自己修。邮件核心那一侧的问题（入口脚本、镜像里的配置）也不要改，写进报告。
