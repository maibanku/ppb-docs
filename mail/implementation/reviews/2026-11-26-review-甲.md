### 2.2 跨邮箱访问——有问题（发现 1）

查了什么：

- **身份注入**：成员面 36 条契约路由全部声明了 `operator: operatorId`（`contracts-mail/api/mail-member-http.json`，逐条看过）；平台契约桥在绑定完请求体和查询串之后，用登录凭据**覆盖式**写入操作者字段（`platform-sdk/servicehttp@v0.2.3/handler.go:150–152`），客户端带的值不存活。37 个成员 RPC 处理器一律用 `req.GetOperatorId()` 调业务包。

- **带签名的标识**（`internal/mailbox/handle.go`）：
  - 算法：HMAC-SHA256 取前 16 字节，密钥至少 16 字节（`NewCoder` 拒绝更短的）；签的内容是「种类字母 + 全部负载」，段与段用点隔开，每段只能是 base64url 字符（不含点），没有拼接歧义。
  - 比较：`subtle.ConstantTimeCompare`（253 行）。
  - 顺序：先验签，再比对账号主键（192、208、229、176 行），不过都是同一个 `ErrBadHandle`，调用方落 404。
  - 跨账号：17 处解析调用（`download.go`、`folder.go`、`flags.go`、`locate.go`、`messages.go`、`send.go`、`thread.go`）传的都是调用者自己的 `id.Account.ID`。
  - 过期和重放：标识不过期——它是位置（账号、文件夹有效性标识、邮件编号、文件夹名），不是令牌，离开本人的登录态没有用；文件夹重建后有效性标识变了就 404，同一有效性标识下编号不复用。
- **不带签名的标识**：删别名（`internal/mailaccount/alias.go` `DeleteAlias` 锁行后核 `row.MailAccountID != accountID`，不是就 404）；过滤规则（`internal/mailsetting/service.go` 一律先 `ruleRowsOf(id.Account.ID)` 再在里面找）；暂存附件（`send.go:494–504` 验签、验账号、验归属人和过期）。
- **手写的三条成员路由**（两条流式下载、附件上传）登记在成员门的 mux 里（`internal/transport/mail/router.go:108–115`），`TestMemberMiddlewareRunsInsideGate` 守着。两条下载对路径上的两个标识都验签、验账号，并核对「附件标识里的邮件部分就是路径上的那封」；响应头是 `attachment` 加 `nosniff`，文件名去掉控制字符。
- **主账号登录不被记成用户登录**：`internal/delivery/dovecot.go:172` `isMasterLogin`（`auth_user` 和 `user` 不同，或者等于配置的主账号用户名），`pipeline.go:394` 在写登录日志和回写最近登录之前就把它剔掉。
  验证：起了一个只带 passwd-file 的一次性 Dovecot 2.3.19.1，用它实际登录后写出的日志行喂给本包的解析器：
  - 主账号登录成功：`Login: user=<test@example.com>, auth_user=<mailmaster>, …` → `登录成功, master=true`
  - 主账号口令不对：`Disconnected: … (auth failed, 1 attempts in 0 secs): user=<mailmaster>, auth_user=<mailmaster>, …` → `登录失败, master=true`（和代码注释说的一致）
  - 用户本人登录成功、失败 → `master=false`

### 2.4 并发下的重复——单实例下通过；两处次要（发现 7）

- **同一个幂等键并发只发一封**：`send.go:114–115` 先拿进程内按键（用户标识 + 幂等键）的互斥，持锁期间「查记录 → 发送 → 写记录」。`idempotency.go:39–65` 的锁我逐条走过三个请求交错的情形，没有死锁，也没有漏放。表上有唯一键 `(owner_user_id, idempotency_key)`。
  验证：一次性测试，20 轮、每轮 64 个同键请求同时起步，每轮提交端口只收到 1 次、结果一致（通过）；仓库自带的 `TestSendIdempotencyConcurrent` 在内存 SQLite 和 MySQL 8.0.45 上都过。
- **两个请求同时申请同一个地址只成功一个**：开通邮箱、添加别名、修改主地址三条路都经 `withClaimedAddress`（`mailaccount/provision.go:355`）：事务里的第一句读就是 `SELECT … FOR UPDATE` 锁域行（`repo_address.go:69–83`），之后才查主地址表、别名表、域保留地址表。MySQL 默认的 REPEATABLE READ 下，读视图在第一句普通读时建立，所以等锁的那个事务拿到锁之后的查重能看到上一个事务刚提交的行。
  验证：一次性 MySQL 8.0.45 容器，仓库自带的 5 个并发用例（同地址、跨表、同用户、不同地址、并发改址）全过；另写了一个加压用例，40 轮、每轮 24 个请求（12 个申请做主地址、12 个申请做别名）抢同一个地址，每轮恰好一个成功、库里这个地址合计一行（通过）。

### 2.5 密码哈希能被 Dovecot 验证——通过

- `internal/platform/argon2id/argon2id.go`：存的是 `{ARGON2ID}$argon2id$v=19$m=19456,t=2,p=1$<盐>$<摘要>`，盐 16 字节随机、摘要 32 字节，都是不带填充的标准 base64（`RawStdEncoding`）。算哈希的只有四处（开通、改密、重置、启动时给主账号算），都用这一个包。列宽 `VARCHAR(255)`（整串 107 个字符）。
- 到 Dovecot 的路：`mail_account.password_hash` → 视图 `v_mail_dovecot_passwd`（只含状态正常、临时密码没过期的账号）→ `dovecot-sql.conf.ext` 的 `password_query` 原样返回带 `{方案}` 前缀的串；主账号走 passwd-file，行形 `<用户名>:{哈希}::::::allow_nets=<网段>`，渲染前用正则核对形态（`render/content.go:139`）。
- 验证（Dovecot 2.3.19.1+dfsg1-2.1+deb12u7）：
  1. `doveadm pw -s ARGON2ID -p <口令> -t <本包现算的哈希>` → `(verified)`；换口令 → `Password mismatch`；仓库里的固定向量同样 `(verified)`。
  2. 反方向：`doveadm pw -s ARGON2ID` 生成的串（`m=65536,t=3`）本包的 `Verify` 通过。
  3. 真登录：用户文件里放本包算的哈希，用明文 IMAP 实际 `LOGIN`，口令对成功、口令错 `Authentication failed`；主账号文件里放本包算的哈希，经本包的 `Client.Open`（登录名 `邮箱*主账号`，主账号表 `master=yes pass=yes`）登录并只读打开收件箱成功；主账号口令错时被拒（`ErrAuthRejected`）。

### 2.6 身份和权限的门

- **成员门**（`router.go:117–121`）：平台的 `svcauth.MemberAuth`——HS256 算法白名单、exp 必须有、typ 必须是 member（管理端 token 进来 403 USER-0003）、sid 必须有、IAM 会话复检和组织成员复检缺一就拒（都是 fail-closed）。本域关掉了 edgeauth 兼容分支，并且进门前摘掉查询串里的 token（`headerOnlyCredentials`），所以拿网址当下载链接这条路走不通。
- **管理门**：
  - HTTP 面（`manage/http.go`）：`svcauth.ManageAuth` 只认 typ=manage → 平台管理处理器按契约里每条路由的 `app_perm` 政策复检（authzguard 回源 IAM）；55 条管理路由全部带政策（逐条看过 `mail-manage-http.json`）；没登记的路由 403；复检拒绝换成本域的 MAIL-2101。
  - RPC 面（`manage/authz.go`）：断言通道——HMAC-SHA256、常数时间比较、绑定 RPC 方法、30 秒有效（验证侧上限 2 分钟），按 IAM 的 mail 应用判，`is_super` 不通配；旧通道按 metadata 里的操作者回源，缺操作者、多值、回源失败都拒。授权用的方法名和路由用的是同一份 rpcinfo；不带服务名的方法调用落到成员服务，够不到管理方法。
  - 手写路由：两条流式下载、附件上传在成员门之内；投递日志导出经 `ManageMount` 套了 `gate.Require("mail.log.read")`（`cmd/server/wire_ops.go:404–406`），这个门先验 IAM 断言（绑定「HTTP 方法 + 路径」，和平台处理器同样的写法），再认管理端 token 并复检权限。
- **RPC 入口**（`cmd/server/boot_wire.go:253–262`）：所有非豁免方法都要求内部凭据（常数时间比较；没配置一律拒）；管理方法再过逐方法授权。
- **匿名接口**（转发确认）：验签在查库之前，签名不对不触发任何查询；令牌是 128 位随机数加签名，库里只存它的 SHA-256，一次性、48 小时有效（`mailaccount/token.go`、`forward.go` `ConfirmForward` 里锁行、核过期、常数时间比较哈希、用完即清）；确认接口的文案两句都不带邮箱地址，响应里只有 base。

### 2.7 入口的大小和速率限制

- JSON 请求体：成员面契约桥和管理面都是 1 MB（`router.go:106、124`），超限 413 MAIL-1016，下游不会被调用。
- 上传：`http.MaxBytesReader`（单个附件上限 + 64 KB），边收边落盘，超限删文件回 413；落盘路径是「用户标识目录 + 随机文件名」，没有任何用户输入进路径。
- 限速：按成员标识分读 300、写 60、上传 30 三个一分钟的固定窗口（`mailbox/ratelimit.go`），排在登录态之后；上传只认 `POST /api/v1/mail/attachments` 这一个确切的「方法 + 路径」，别的写法进不了上传类。超限 429 MAIL-4291，`Retry-After` 是到窗口结束的秒数。

问题：发现 6（出站限额那个 429 的 `Retry-After` 恒为 1）。

### 2.8 控制面对外的连接

- 内部提交端口：明文 TCP、不认证（设计如此，靠来源限制），每一步有超时，每次新建连接。
- IMAP：隐式 TLS、最低 TLS 1.2、校验证书和主机名；主账号口令从环境变量读一次，只用于 `LOGIN`。
- 运维代理：Unix 套接字，一次连接一个 JSON 请求；队列标识、邮箱地址、脚本路径在发出去之前都校验；代理回的错误原话只进日志。
- Rspamd 控制接口：节点内部的 HTTP，口令放在请求头里，每次用时才读环境变量；客户端不走环境里配的代理，错误里不带请求头。
- IAM、IM 的 gRPC：内部凭据拦截器（没配置就在本地拒绝、不外呼），到 IAM 的连接另加断言签发拦截器；适配器把 nil 响应、Base 不是成功一律按失败处理。

问题：发现 4（策略服务的来源名单在生产环境可以留空）。

  ```
  MoveMessages 到已发送：成功 1、失败 0
  已发送里第 2 封（追踪号 <victim-id@remote.example>）的投递情况：hidden-bcc@example.org 状态=1
  已发送里第 2 封（追踪号 <victim-id@remote.example>）的投递情况：zhangsan@example.org 状态=1
  ```
- **建议**：`ByMessageID` 带上调用者的条件——只返回出站、且 `sender_address` 是本人主地址或本人别名的行（提交端口上没有 SASL 登录，`auth_account` 多半是空的，所以按发件人过滤；SMTP 提交那条路有 `reject_authenticated_sender_login_mismatch` 保证发件人是本人的地址）。同时 `GetDeliveryStatus` 先核对这封信的 From 是本人地址，并把结果限定在这封信头的收件人里。加一条测试：把收到的信挪进已发送后查投递情况，不返回别人的收件人。

### 发现 2（重要）关闭「允许用户自助设置转发」后，已有的自助转发照常生效

- **位置**：`internal/mailaccount/forward.go:327`、`forward_verify.go:28、75`（这个开关只在设置、重发确认信、确认这三处读）；`internal/dbmigrate/migrations/000001_mail_schema.up.sql:507–514`（视图 `v_mail_alias` 的转发分支只看 `enable_flag`、`verify_status`，和这个设置没有关系）；`internal/mailsetting/service.go:540`（过滤规则的转发动作也只在保存规则时看这个开关）；`internal/mailbox/forward.go:58`（界面显示的 `Enabled` 同样不看它）。
- **场景**：管理员在全局设置里把「允许用户自助设置转发」关掉（比如发现有人在把公司邮件转到外面，要一刀切）。结果是：新的自助转发设不了了（403），待确认的确认不了了，但**所有已经验证过的自助转发还在转发邮件**，已经建好的「转发到地址」过滤规则也还在转。设计和验收都说不生效：`tech/06` §8.4 第 4 条「已有的转发设置保留但不生效，重新开启后恢复」，`tech/07` 把这个设置标成「即时」。
- **证据**：在迁好结构的一次性 MySQL 上执行——
  ```sql
  INSERT INTO mail_setting (…'member_forward_enabled','true'…);
  INSERT INTO mail_forward (…enable_flag=1, verify_status=2, forward_source=1…);   -- 用户自助、已验证、启用
  SELECT … FROM v_mail_alias WHERE address='zzfwd@zzfwdtest.example';
  UPDATE mail_setting SET setting_value='false' WHERE setting_key='member_forward_enabled';
  SELECT … FROM v_mail_alias WHERE address='zzfwd@zzfwdtest.example';
  ```
  输出：
  ```
  before: member_forward_enabled=true
  view while on: zzfwd@zzfwdtest.example -> zzfwd@zzfwdtest.example,zz-outside@example.net
  after: member_forward_enabled=false
  view while off: zzfwd@zzfwdtest.example -> zzfwd@zzfwdtest.example,zz-outside@example.net
  ```
  全仓 grep `KeyMemberForwardEnabled` 只有上面三处读取，没有任何代码在开关变化时改转发行；`mailconf.Store` 也没有变更回调。
- **建议**：让别名视图读得到这个开关（转发分支加上「`forward_source = 2`（管理员设置）或者 `member_forward_enabled` 为真」，视图里关联 `mail_setting`，或者在设置变更的同一个事务里把自助转发的行改成不生效、并记住原来的启用状态以便恢复）；开关关闭时已有的「转发到地址」规则也要停（重渲染脚本时去掉 `redirect`）。加一条 MySQL 上的测试：开关关掉后视图里查不到这个转发、重新打开后回来。

### 发现 3（重要）过滤规则里的「转发到地址」不需要验证目标地址

- **位置**：`internal/mailsetting/service.go:535–544`（`ActionForward` 只校验地址格式和「管理员是否允许用户转发」）；`internal/mailsetting/sieve.go:121`（渲染成 `redirect "…";`）。
- **场景**：成员建一条过滤规则，动作选「转发到地址」，填任意一个格式正确的地址——不需要对方确认，立即生效，之后命中的来信都被重定向到这个地址。这绕开了转发那条路上的验证（S18-3、验收 MAC-38「未验证时不转发」）：填错了，邮件就静默地发给了一个陌生人，对方没有任何确认的机会；想用系统把来信转给没同意过的第三方也没有拦。
- **证据**：
  ```go
  // mailsetting/service.go:535–544
  case ActionForward:
      addr, err := mailbox.ParseAddress("", in.Action.ForwardAddress)
      …
      if !s.forwardEnabled() { return mailerr.ErrMemberForwardDisabled }
      in.Action.ForwardAddress = addr.Address
  // mailsetting/sieve.go:121
  return "redirect " + sieveQuote(a.ForwardAddress) + ";"
  ```
  现有测试 `internal/mailsetting/service_test.go:244–249、330–338` 只断言地址格式和开关。需要说明：这和设计 S17-6（「转发动作只在管理员允许用户转发时可用」）是一致的，和 S18-3 冲突的是设计本身；这里按「使用的人会得到什么」报，需要负责人决定。
- **建议**：两个选项。(a) 转发动作的目标地址必须是这个账号已经验证过的转发地址（复用 `mail_forward` 的验证状态），或者单独发一封确认信；(b) 至少在界面和契约里写明「转发到地址不确认对方」。按 MAC-38 的字面，建议 (a)。

### 发现 4（次要）策略服务的来源名单在生产环境可以留空，留空时谁能连上谁说了算

- **位置**：`internal/transport/postfixpolicy/server.go:207–210`（名单为空时 `sourceAllowed` 恒为真）；`internal/transport/postfixpolicy/protocol.go:94–120`（请求里的 `sasl_username` 直接当作要判定的账号）；`internal/outbound/service.go:276–294`（`Admit` 每问一次就给这个账号计一个收件人）；`internal/config/config.go:568–596`（`validateProd` 要求了 `master_allow_nets`，没有要求 `policy_allowed_clients`）；`env/mail-prod.template.yaml:47–48`（缺省监听 `0.0.0.0:11433`，名单是 `[]`）。
- **场景**：生产环境按模板部署，策略端口不校验来源。能连到这个端口的进程（`mailnet` 上的容器、宿主机上的进程）伪造 `protocol_state=RCPT` + `sasl_username=<某人>` 的请求：每发一次就扣掉这个人一个收件人的出站额度，直到他被限额；回包还是一个探测口——`DUNNO` 是有外发权限的账号、`REJECT` 是没有或不存在、`DEFER` 是额度用完了。代码注释自己写了这一点（`server.go:91–94`），但没有在生产门禁上兜住。
- **证据**：一次性测试（包 `postfixpolicy`）用 `127.0.0.1` 去连：
  ```
  allowed=[]                 判定器被调用 1 次，回言行="action=DUNNO\n"，PassCounted=1 RejectedSource=0
  allowed=[203.0.113.10]     判定器被调用 0 次，回言行="" 读错误=connection reset by peer，PassCounted=0 RejectedSource=1
  ```
  正式编排里 11433 没有发布到宿主机，所以这是纵深防御缺了一层，不是对外暴露。
- **建议**：`validateProd` 加一条——生产环境必须配置 `mail.policy_allowed_clients`（和 `master_allow_nets` 同样处理）；生产模板把它写成邮件核心容器的地址。注意配套：配上名单之后 `/healthz` 里「策略端口在监听」的那次自连（`cmd/server/wire_ops.go:424–437`）也会被名单拒掉，每次健康检查多一行告警日志和一次 `rejected_source` 计数，要一起改（比如名单固定放行回环地址，或者改成进程内检查）。

### 发现 5（次要）线上的 SQL 日志器在语句失败或变慢时把参数值原样写出

- **位置**：`internal/platform/db/open.go:95–101`（`productionLogger`，没有打开 `ParameterizedQueries`）。
- **场景**：写 `mail_account` 的语句失败（撞唯一索引、死锁、锁等待超时）或者超过 200 毫秒时，GORM 把整条语句连同参数值写到标准输出，也就是容器的日志里——里面是邮箱口令的 Argon2id 哈希。开通邮箱撞唯一索引这条路代码里是明确处理过的（`provision.go:178–188` 的 `isDuplicateKey` 分支），所以不是纯理论。明文口令、令牌、私钥、连接串不会经这条路出去（它们不在参数里，或者不进 SQL）。
- **证据**：一次性测试（包 `db`，真的 MySQL，日志器输出接进内存）：让一条同时改主地址和口令哈希的 `UPDATE` 撞唯一索引，日志里有：
  ```
  [2.8ms] [rows:0] UPDATE mail_account SET mail_address = 'zz-b@example.com', password_hash = '{ARGON2ID}$argon2id$v=19$m=19456,t=2,p=1$REVIEWREVIEWREVIEWRE$REVIEW…' WHERE mail_account_id = 9900000000000000
  ```
- **建议**：`gormlogger.Config` 里加 `ParameterizedQueries: true`（日志里只留占位符）。这是平台各服务共有的缺省行为，改本包的 `productionLogger` 一处就够。

### 发现 6（次要）出站限额的 429 带的 `Retry-After` 恒为 1 秒

- **位置**：`internal/transport/mail/httperr.go:22`（`DefaultRetryAfter` 固定回 1，全仓没有别处替换它）；`internal/transport/mail/httpmw.go:52–71`、`router.go:106–108`（契约桥外面套的 `EnsureRetryAfter`）；`internal/mailbox/send.go:158–164`（真实的等待时间只写进了文案）。
- **场景**：发送接口因为出站限额回 429 MAIL-4290，文案说「请在 N 秒后重试」（N 可能是几十到几千秒），响应头却是 `Retry-After: 1`。按响应头重试的客户端会每秒重试一次，直到撞上成员写限速（60 次/分钟）变成 429 MAIL-4291。限速那个 429 的头是对的。
- **证据**：一次性测试（包 `mail`，用路由测试里的假回环调用器让 RPC 回 429 MAIL-4290）：
  ```
  状态 = 429, Retry-After = "1"
  ```
- **建议**：契约响应里加一个「建议等待秒数」的字段，由契约桥照它写 `Retry-After`；或者退一步，让发送接口的缺省值不小于出站限额最小窗口的秒数，别给 1。

### 发现 7（次要）幂等在两种情况下挡不住重复发送

- **位置**：`internal/mailbox/send.go:117–121`；`internal/mailbox/idempotency.go:5–6`（注释）、`125–136`（`idempotencyPut`）。
- **场景和证据**：
  1. **查幂等记录出错时放行**。第一次发送成功并写下了记录；客户端用同一个键重试，恰好赶上读库出错（`send.go:118–120` 只记一条告警，`stored` 为 nil 就照常往下发）。一次性测试（包 `mailbox`，给幂等表的查询挂一个报错的回调）：
     ```
     重试：提交端口收到的次数 2（之前 1），返回码 ""
     ```
  2. **多实例**。注释说唯一键是「第二道：多实例或者互斥没拦住时，后写的那个会撞唯一键，撞了就按已存在的记录走」，但 `idempotencyPut` 撞键之后是**删掉旧记录再写新的**，不会去读旧记录。一次性测试（两个 `*mailbox.Service` 共用一个 MySQL，提交端口处设栅栏让两边都走到这一步）：
     ```
     两个实例、同一个幂等键：失败的请求 0 个，提交端口收到 2 次
     Error 1062 (23000): Duplicate entry … for key 'mail_idempotency.uk_mail_idempotency'
     ```
     现在的部署是单节点单实例（编排和 `tech/09` §2.5 都这么说），所以这条现在不会发生；报出来是因为注释的说法不成立，以后要横向扩容的人会被它误导。
- **建议**：查幂等记录出错时不放行（回 MAIL-9001，让客户端稍后重试，那时记录已经在了）。多实例：要么在提交之前先插一条「进行中」的记录，靠唯一键挡住并发，撞键的那个等一等再读第一次的结果；要么把注释改成「不支持多实例」并写进部署文档。

## 4. 没去评判的

- 平台的内部信任模型：持有 `PPB_INTERNAL_RPC_TOKEN` 的任何进程都能直连 RPC 端口（9108，发布在 `BIND_PLATFORM` 上）以任意 `operatorId` 调成员方法，或者自己签一枚 IAM 断言调管理方法。这是平台各服务共用的约定，不是本仓引入的，没法在这里下结论。
- 到 MySQL、IAM、IM、Rspamd、策略服务的连接在网络里是明文的，靠网络隔离。部署和平台的约定。
- 主账号的登录失败被整体剔除（这是要求的行为），所以「认证攻击」告警看不到有人在外面猜主账号口令。Dovecot 的失败惩罚会把单一来源的尝试压到每小时个位数，告警阈值是每小时 50 次，本来也够不着；不作为发现。
- 近期认证那个退而求其次的做法的两个漏洞（`mailbox/reauth.go` 文件头写了），归评审员乙。
- 暂存附件「每个用户的暂存总量」是先查后插，并发上传能略超（`mailbox/attachment_temp.go:158–189`）；同一个邮箱在两个域里同时加别名时数量上限不被串行化（`mailaccount/alias.go:183–225`）。都是上限的小偏差，分别归评审员乙和丙。
- IAM 业务桥那条路上管理员的写操作拿不到数字的操作者标识（断言里的 `Actor` 是业务键），会回 MAIL-1001。是功能问题不是安全问题，归评审员丙。
- 设计 `tech/09` §2.4 说兼容请求头 `Idempotency-Key`，实现没有做（只读请求体）。带了头不带体的客户端会得到 MAIL-1001，不会静默重复发送。
- 邮件核心（Postfix、Dovecot、Rspamd 的配置，运维代理那一侧）不在范围内；我只读了给第 1、5 两类下结论必须读的那几处。
- 多实例那个验证是在一个进程里用两个 `*mailbox.Service` 模拟的，不是两个真实进程；结论依赖的是代码路径，不是进程边界。
- 改密码时猜当前口令没有失败次数限制（要先有成员登录态，写接口又限 60 次/分钟）。没有评估。

## 5. 核过、确认没问题的高风险点

- 未认证向外部投递被拒、提交端口只认已认证会话、内部提交端口只放行控制面地址（邮件核心的 Postfix 配置，为给结论核过）。
- 控制面发件地址归属的校验在提交之前；信封发件人就是校验过的那个；提交端口没有第三个调用方。
- 成员面 36 条、管理面 55 条路由的操作者字段都由登录凭据覆盖，客户端带的值不生效。
- 成员门、管理门、RPC 入口的内部凭据和逐方法授权；手写的四条路由都套了门。
- 匿名的转发确认接口不泄露信息（先验签后查库、常数时间比较、一次性、48 小时、文案不带地址）。
- 带签名的标识：算法、常数时间比较、账号绑定、没有跨账号使用的路径；不带签名的别名标识、规则标识、暂存附件标识都按本人账号限定。
- 主账号登录（成功和口令不对的失败）不会被记成用户登录（真实 Dovecot 日志行验证）。
- 口令哈希能被 Dovecot 2.3.19.1 验证（`doveadm pw -t` 双向、真实 IMAP 登录、主账号登录）。
- 同一个幂等键并发只发一封（64 并发 × 20 轮）；同一个地址并发申请只成功一个（24 并发 × 40 轮，MySQL 8.0.45 REPEATABLE READ）。
- 日志、错误信息、配置摘要、审计里没有口令、令牌、私钥、完整连接串；`-check-config` 没有副作用；生产环境关不掉 IMAP 的证书校验，缺秘密、用开发默认值都起不来。
- 渲染进 Postfix、Dovecot、Rspamd 配置的值有校验（数据库口令的字符集、域名和选择器、私钥路径、白名单条目、主账号哈希的形态），模板替换拒绝换行和残留的占位符。
- 列表的排序列走白名单，搜索串转义了通配符，没有拼接的 SQL。
- 成员面的 JSON 上限 1 MB、上传上限、三个限速窗口和 429 的 `Retry-After`（限速那个）。
