## 3. 发现

按严重度排。没有「严重」。

### 重要

#### 丙-1 加了域或轮换 DKIM 之后，出站邮件不带 DKIM 签名，直到有人手工给 Rspamd 发 HUP

- **位置**：`internal/render/apply.go:41-52`（`RenderDKIM` 写完文件只记一条告警日志，返回 nil）；`internal/maildomain/domain.go:134, 432-444`、`dkim_ops.go:87, 145`（`renderDKIM` 渲染成功时不向调用方返回任何告警）；`contracts-mail/proto/mail.proto:1454-1458`（`CreateDomainResp` 没有告警字段）；`mail-manage-web/src` 里 grep 不到「HUP」「重新读取」这类提示。邮件核心的说明：`deploy/config/rspamd/README.md:13`、`deploy/docs/runbook.md:214`。
- **场景**：部署后控制面先起来，这时库里一个域都没有，`dkim_signing.conf` 渲染成空的 `domain {}`；邮件核心的 Rspamd 接着启动，读到的就是这份空的。管理员在管理台添加第一个域，照页面给出的记录把 DNS 配好，用户开始发信——Rspamd 还在用启动时读到的配置，这些邮件没有 `DKIM-Signature`，直到有人在邮件服务器上执行 `docker compose kill -s HUP rspamd`。之后每加一个域、每次轮换都是这样。收件方看到的是「没签名」，严格的收件方直接进垃圾箱或拒收。
- **证据**：读代码加邮件核心的文档。Rspamd 只在启动或收到 HUP 时读模块配置，`dkim_signing.conf` 是控制面运行期才重写的；控制面没有任何途径把「需要重载」告诉管理员——只有一行日志。全局设置那边的同类情况（关灰名单、开病毒扫描）是在接口的 `warnings` 里回给管理台的，域名这边没有。
- **改法**：控制面这一侧的最小改法：`CreateDomain`、`RotateDKIM`、`DeleteDKIM` 的响应带上告警（契约没有字段就加），管理台在「域已添加」和域名详情页一直显示「签名配置还没生效，要在邮件服务器上执行 …」。根治在邮件核心（不在这次范围内，提一下）：Rspamd 容器的入口脚本盯着 `dkim_signing.conf` 的修改时间，变了就 `kill -HUP 1`。

#### 丙-2 口令哈希会随 SQL 日志写出来

- **位置**：`internal/platform/db/open.go:95-100`（线上句柄的 SQL 日志器：`LogLevel: Warn`、`SlowThreshold: 200ms`，没有开 `ParameterizedQueries`）。受影响的语句：`mail_account` 的插入和整体写回（`mailaccount/repo_account.go` 的 `insertAccount`、`saveAccount`，写回是 `Select("*")`）、`mail_account_password_history` 的插入。
- **场景**：任何一条带 `password_hash` 的 INSERT/UPDATE 出错——包括设计里就有的「同一个用户并发开通，输的一方撞唯一索引」（`provision.go:178-183`）——或者这一条耗时到了 200ms（行锁等待、数据库忙），GORM 就把带着参数值的整条语句打到标准输出，也就是容器日志。
- **证据**：一次性 MySQL 上用线上的句柄（`db.Open`）实测，把标准输出接到管道里：
  - 同一个用户再插一行 → `Error 1062: Duplicate entry '77001' for key 'mail_account.uk_mail_account_user'`，捕获到的日志里有 `INSERT INTO mail_account (…password_hash…) VALUES (…,1,0,1,'HASHMARKER-ERROR-PATH',NULL,…)`。
  - 另一个事务先锁住这一行约 450ms，再让 `saveAccount` 写回 → 写回成功（没有错误），日志里有 `UPDATE mail_account SET … password_hash='HASHMARKER-ERRO…'`。
  - 测试里的内存句柄把日志器关成了 Silent，所以平时的测试看不到这件事。
- **说明**：实际暴露面有限——是 Argon2id 的哈希，策略要求 12 位起，离线破解不现实；触发条件（出错或超过 200ms）不常见，备份脚本用了 `--single-transaction`，不会把写入卡慢。但它违反这个库自己的规矩（审计里连哈希都不放），改法是一行，所以放在「重要」。
- **改法**：`productionLogger` 里加 `ParameterizedQueries: true`（GORM 只打 `?`，不打值）；加一个测试，对着线上句柄做一次会出错的账号写入，断言日志里没有哈希。

#### 丙-3 HTTP 发信的出站限额：`Check` 不预占计数，并发请求都过 `Check` 再各自 `Add`

- **位置**：`internal/outbound/service.go:300-316`（`Check` 只判断、不计数）、`:319-325`（`Add` 只累加）；调用方在成员邮箱：`internal/mailbox/send.go:150`（提交前 `Check`）、`:182`（服务器接收后 `Add`）。
- **场景**：每小时上限 200。一个脚本同时发 10 个请求、每个 100 个收件人：10 个 `Check` 都看到「还剩 200」而放行，全部提交之后计数是 1000。标准客户端那条路不受影响——策略服务的 `admit` 是判断和累加在同一把锁里一步完成的。
- **证据**：一次性测试（带 `-race`）：10 个并发各 100 个收件人，`Check` 放行 10 个，`Add` 之后合计 1000；这之后再查 1 个收件人才被拒。
- **说明**：调用方在评审员乙那一栏，建议两个人对一下这条。
- **改法**：`Check` 改成预占（就是 `admit`），提交失败或没被服务器接收时退还；或者改成先计数、失败回滚。

### 次要

#### 丙-4 保留地址（postmaster、abuse）指向的邮箱被彻底删除之后，保留地址悬空

- **位置**：`internal/mailaccount/status_ops.go:271-322`（彻底删除不看有没有保留地址指着它）；`alias.go:126-140`（管理员删别名同理）；视图 `v_mail_alias` 里系统别名那一段对目标不做存在性判断（`internal/dbmigrate/migrations/000001_mail_schema.up.sql:493-516`）；只有设置保留地址时才要求目标存在（`maildomain/alias.go:63-78`）。
- **场景**：域的 postmaster 和 abuse 指向管理员邮箱。这个邮箱被删除，保留期满彻底删除。`postmaster@域` 仍然指向一个不存在的地址，Postfix 改写之后投不出去，发件人收到退信；系统里没有任何提示。M06-3 写的是「保证这两个地址总能收到信」。
- **证据**：一次性测试：建域 `sysalias.example`（两个保留地址都指向 `postbox@example.com`）→ 删除并彻底删除这个邮箱 → `mail_system_alias` 的两行还是 `-> postbox@example.com`，而这个地址在主地址表和别名表里都是 0 行。
- **改法**：彻底删除、删别名之前查一下有没有保留地址指着它：拒绝并说明「它是 postmaster@x 的目标」，或者允许但在系统状态页标出悬空的保留地址。

#### 丙-5 日志采集器先记断点、后入库：入库失败或进程在两步之间被杀，这一轮读到的行永久丢失

- **位置**：`internal/delivery/collector.go:384-391`（读完一个文件就 `saveFileCheckpoint`，内存里的游标同时前移）、`:305-319`（两个源都读完才 `flush`）、`:557-601`（`flush` 出错时攒下的行照样丢掉）、`:638`（去重缓存在插入之前就登记了这些键）。同一个包里的评分记录采集是先入库、后记游标（`history.go:274-282`）。
- **场景**：数据库抖一下，这一轮的 INSERT 失败；或者控制面在「记完断点、还没入库」之间被 OOM 杀掉。断点已经越过了这些行，之后同一个进程和重启后的进程都从新断点接着读，这些投递记录和登录记录不会再被读出来。优雅停机不受影响（停机前完整跑一轮）。设计的目标是「不重复不遗漏」，重复靠唯一索引挡住了，遗漏在这种情形下挡不住。
- **证据**：一次性测试：给 `mail_delivery_log` 的插入注入一次失败 → `Poll` 返回「写入日志行（1 行）: 库抖了」，断点 offset=611 已经前移；之后同一个进程再采、再追加一封正常的、再「重启」两次，库里只有后一封，失败那一轮读到的那封（`6E67A56E32`）不在。仓库里已有的重启用例只覆盖了「入库成功之后重启」。
- **改法**：顺序反过来：这一轮的行落库成功之后再写断点；入库失败时游标不前移、行留着下一轮重试；去重缓存改成插入成功之后再登记。

#### 丙-6 彻底删除不清配额记录，地址重新分配之后新邮箱带着旧用量

- **位置**：`internal/mailaccount/repo_account.go:153-170`（`deleteAccountTree` 有意不删 `mail_quota_dict`）；运维代理的 `mailbox.delete` 也只删邮件目录和 Sieve 目录（`deploy/images/mailcore/mailops/internal/commands/commands.go:621-660`）；管理台的已用容量按地址直接关联这张表（`repo_account.go:81`），容量预警也按它（`quota_warning.go:74-82`）。
- **场景**：甲离职，邮箱删除，30 天后彻底删除；之后给乙开通同一个地址。乙的邮箱在管理台一开始就显示甲的已用容量；甲用到配额 90% 以上的话，每日维护还会给乙发一封容量预警。M10-3 列的清除内容里有「配额记录」。
- **证据**：读代码——库里没有任何路径删这张表的行，控制面的句柄对它只读。Dovecot 自己会不会在乙第一次登录时重算，没在真实组件上核对（代码注释说会）。
- **改法**：运维代理的 `mailbox.delete` 里加一步 `doveadm quota delete -u <地址>`；核实之前，至少在重新分配一个用过的地址时给管理员一句提示。

#### 丙-7 审计写失败时的行为不统一

- **出站限额的默认值不回滚，重试之后这次变更在审计里没有痕迹**。`internal/outbound/admin.go:179-203`：先保存设置，再写审计；审计写不进去只报错，设置已经生效，接口回 MAIL-9001。管理员看到失败、用同样的值再提交一次：值没变，不算变更，不写审计。一次性测试：第一次返回 MAIL-9001，默认值已经是 {300, 2000}；审计恢复后重试返回成功，审计 0 条。对比：设置页的 `UpdateSettings` 审计写不进去会把设置回滚（`manage/settings_kitex.go:98-105`）。改法：审计写进和设置同一个事务，或者失败时回滚。
- **彻底删除和队列操作先记一条「成功」，失败后再补一条「失败」**。`mailaccount/status_ops.go:283-293`、`audit.go:96-112`；`mailqueue/write.go:185-194`。这是「放不进同一个事务的先写审计」的做法，但审计里同一个动作会同时有成功和失败两条。一次性测试：彻底删除在删邮件目录这一步失败 → 审计里 `account.purge result=1` 和 `account.purge result=2` 各一条（邮箱正确地保持待删除）。改法：给「已开始、结果未知」一个单独的结果值或动作码，执行之后补最终结果。
- **手动触发对账：正在跑的时候再触发，静默返回成功，还记一条成功审计**。`accountsync/sync.go:207-213`（已经在跑就返回 nil）；`manage/sync_kitex.go:102-114`。另外这里的审计写在触发之后，审计失败时对账已经在后台跑了。改法：正在跑时回一个明确的业务码，不记成功审计。
- **设置页被拒绝的修改不记失败审计**。`manage/settings_kitex.go:84-93`：越界或联动校验不过直接返回。账号、域名、黑白名单、出站限额的被拒都记。改法：被拒时补一条。

#### 丙-8 别名总数的上限在跨域并发下会被突破

- **位置**：`internal/mailaccount/alias.go:198-212, 236-255`。加锁锁的是别名所在域的域行，计数是按邮箱数的。
- **场景**：一个邮箱已经有 19 个别名，同时在两个域里各加几个：两个域的域行互不阻塞，两边都数到 19 而放行，总数成了 21（上限 20）。自助的上限（5 个）同理。
- **证据**：一次性测试 10 轮，全部是「19 个之后并发加 6 个，成功 2 个，总数 21」。
- **改法**：计数之前把账号行也锁住（`lockAccount`；次序仍然是域行 → 账号行，和改主地址一致）。

#### 丙-9 对账范围是「指定组织」时，工号不合规的成员永远开通不了

- **位置**：`internal/accountsync/sync.go:68`（`accountNameRe` 允许 1 到 64 位、不查保留字）、`:463-469`（`localPartFor`）。对比按组织开通那条路：`internal/mailaccount/provision_org.go:235-241` 用的是 `NormalizeLocalPart`，不合规就用用户标识。
- **场景**：组织里有工号是「01」「12」「admin」或者超过 32 位的成员。每一轮对账都去给这些成员开通，被 MAIL-1017 拒绝，计进失败数，下一轮照样。这些成员永远没有邮箱；除了每轮一条告警日志和运行记录里的失败数，没有别的信号（「对账连续失败」的告警数的是整轮失败，不是单条）。
- **证据**：一次性测试，接的是真的账号服务：工号 `zhang.san`、`x.y` 的开通了；`01`、`admin`、40 位的第 1 轮新建 2 失败 3，第 2 轮新建 0 失败 3。
- **说明**：这个范围在当前平台本来就用不了（后台任务调 IM 的 ListMembers 会被拒），所以现在碰不到；代码留着，哪天平台开了口子就会表现出来。
- **改法**：`localPartFor` 改用 `NormalizeLocalPart`（或者把同样的规则搬过去），不合规就用用户标识。

#### 丙-10 策略服务的来源名单在生产模板里是空的，生产环境的配置校验也不强制

- **位置**：`service-mail/env/mail-prod.template.yaml:48`（`policy_allowed_clients: []`，注释写「建议配上」）；`internal/config/config.go:442-447, 568-592`（生产环境要求 `master_allow_nets` 非空，对这一项没有要求）；`internal/transport/postfixpolicy/server.go:207-230`（名单为空一律放行）。
- **场景**：照模板部署。邮件网络上的任何容器都能连 `11433`，带上 `sasl_username=<别人的邮箱>` 发 200 个请求，把这个邮箱这一小时的外发额度用完（他发信得到 451）；或者用 REJECT 和 DUNNO 的差别探出谁的账号停用了、谁关了外发。端口不发布到宿主机，所以攻击面是同一个网络里的其他容器。
- **改法**：`validateProd` 里和 `master_allow_nets` 一样要求非空；模板里给出邮件核心的地址或网段。

#### 丙-11 停用的域里还能改主地址

- **位置**：`internal/mailaccount/update.go:93-101`（管理员）、`:125-140`（用户自助）。加锁流程不查域的状态。开通（`provision.go:226-233`）和加别名（`alias.go:195-197`）都是拒绝的。
- **证据**：一次性测试：域停用之后加别名回 MAIL-1019；管理员改主地址、用户自助改主地址都成功，新地址落在停用的域里。
- **改法**：两条改地址的路径在加锁前查一下域的状态。

#### 丙-12 批量任务的幂等键只在进程内存里，查和记之间没有互斥

- **位置**：`internal/mailaccount/batch.go:243-257`（查）、`:293-295`（记）、`:162-191`（内存表）。
- **场景**：同一个幂等键并发提交 8 次会建 8 个批量任务（动作是停用、删除这类，执行结果幂等，但任务列表和审计里是 8 条）。控制面重启之后键全丢。
- **证据**：一次性测试：批量任务行数 0 → 8。
- **改法**：在键上先抢一把进程内的互斥；或者把键落库，给 `mail_admin_batch` 加 (发起人, 幂等键) 的唯一索引。

#### 丙-13 「主机名或地址变了」的提示，控制面一重启就没了

- **位置**：`internal/maildomain/dns.go:574-612`（`RegisterEndpoint` 把 changed 放在进程内存里）、`:548-566`、`:484-486`；`service.go:59-61`。
- **场景**：改了对外主机名，页面提示要同步改 DNS。DNS 还没改，控制面因为发版重启了一次：配置和登记行一样，changed 是假，提示没了。页面上只剩全局两项的检查结果；那一次后台检查要是「未检测」（查询超时），状态还是原来的值。
- **证据**：读代码。
- **改法**：changed 落库，或者由「最近一次全部通过的全局检查晚于登记时间」推出来。

## 4. 没去评判的

- 管理员删除的邮箱，在保留期内用户在 IAM 注销又恢复，邮箱会被恢复成正常（`status_ops.go:113-127`；一次性测试实测 status 3 → 3 → 1）。代码注释说「管理员自己删除的不会被救回来」，只对「IAM 一直是正常」的情况成立；tech/04 2.3 的表又写「IAM 用户恢复 → 邮箱恢复正常」。两种说法都有依据，留给负责人定。
- `isMasterLogin` 用「`auth_user` 和 `user` 不同」判定主账号登录。邮件核心没有设置 `auth_username_format`（Dovecot 的缺省会把账号名转小写），用户用大小写混写的地址登录时这两个值可能不同，那样的登录会被当成主账号登录而不入库。没有在真实 Dovecot 上核对，所以不作为发现。
- `CleanOrphanKeys`（每日 03:20）和添加域/轮换（先写文件、后写库）之间有一个毫秒级的窗口，撞上会把刚落盘的新私钥当孤立文件删掉。概率极低，没有去构造。
- 单实例的假设贯穿这一栏：域的互斥锁、设置的内存镜像、出站计数器、批量幂等键、日志采集器和策略服务各只有一个。多副本时还要给每个副本配不同的雪花节点号（`idgen` 的说明里有）。按现在的部署方式评判。
- 对账范围是「指定组织」、组织列表不为空而被 IM 拒绝时整轮失败，IAM 状态同步也跟着停（`accountsync/sync.go:335-357`）。这是文档里写明的判断（「不要为了让它绿把这句话吞掉」），告警会响；但它的后果是 IAM 里停用的人邮箱照常能用，直到有人改掉这个设置。没作为发现，负责人知不知道这个后果可以确认一下。
- 审计里的客户端地址永远是空的（接线计划第 4 节：契约处理器读不到请求头）。
- Rspamd 面对同一个域的多个选择器时用哪一把签名、旧私钥文件读不到时怎么表现（`render/sources.go` 的注释自己写了没在真实组件上核对）。属于邮件核心。
- 关灰名单、开病毒扫描也要发 HUP 才生效：这一处在接口的 `warnings` 里提示了，所以没列进发现。
- 策略服务每个收件人都要查一次库取覆盖值（`outbound/service.go` 的 `limits`），没有缓存。小规模下不构成问题，没有做压测。
- 评分记录采集（`delivery/history.go`）只看了它和日志采集器的顺序差异（先入库后记游标，是对的），没有逐项核它的指纹和游标逻辑。
- `mailstatus` 的告警条件、指标和系统状态采集没有逐条核，只看了告警 webhook 的地址不进日志。

## 5. 核过、确认没问题的高风险点

**账号**
- 地址规则和保留字与 M06-1、M06-2 逐字一致；不分大小写、按小写保存；转发目标地址另有一套宽松规则，只用于外部地址。
- 一个用户最多一个邮箱（`uk_mail_account_user`）；重复开通幂等（已有就原样返回，不改动、不报错）；地址在保留期内不会被分给别人（待删除的账号行还占着地址），彻底删除后可以重新分配。
- 口令策略（12 到 128 位、不等于地址、弱口令表）；不得与当前和最近 3 次相同（历史表只留 3 行，管理员开通时填的初始密码也记进历史）；管理员重置不受历史限制。
- 临时密码：`crypto/rand` 加拒绝采样，16 位、去掉易看错的字符；7 天过期。过期后不能登录邮件协议——`v_mail_dovecot_passwd` 排除了 `password_expire_time` 已过的账号；控制面的改密码也拒绝用过期的临时密码（`password_ops.go:100-103`，持锁之后又查一遍）。没设过密码的邮箱存的是一段没人知道原文的随机串的哈希。
- 改密时间：所有让邮箱有了可用密码的路径都写了 `password_changed_time`（开通填的、临时的、重置、改密码、设置初始密码），没可用密码的为空；`InitialPasswordRequired` 的两条判据和成员面一致。
- 状态机：`account_status` 只由 `DeriveStatus` 从三个输入推导（tech/08 5.3 的表逐行一致）；停用、恢复、删除、改密、改地址、改别名都在持锁之后对着最新的一行再查一遍前置条件。恢复时 IAM 状态不是正常的会现场问 IAM，问不到不放行。
- 彻底删除的顺序：先写审计 → 经运维代理删目录（失败则整体失败，邮箱保持待删除，一行不删）→ 事务里再确认还在待删除才删行。物理删除的表覆盖了 7 张按账号归属的表（`mail_idempotency` 和 `mail_attachment_temp` 按用户归属，自带过期）。文件头自己写明的那个「删除和恢复同时点」的窄竞态确实存在，也确实很窄。
- 每日维护的「待删除邮箱清理」单条失败不影响其余；重启后遗留的批量任务在启动钩子里标成中断。
- 账号、别名、转发、批量、状态操作：成功的审计写在业务事务里（审计写不进去业务就回滚），失败的补一条失败审计。

**域名和 DKIM**
- 私钥：RSA 2048 位，`crypto/rand`；先写同目录的临时文件（0600）、改成 0440、属主 5000:5000、改名覆盖；各级目录 0755。先写文件再写库，库写失败的文件不会被拿来签名，每日维护会清掉。
- 轮换：新选择器（`s<年月>`，同月加序号，不回头用旧的）、旧选择器保留并标成不是当前，`dkim_signing.conf` 里新旧并存、当前的排前面；当前签名用的不能删；删域的顺序是事务里删密钥行、保留地址行、域行，提交之后才删文件。
- DNS 校验：单项 10 秒、整轮 60 秒，每台服务器按剩余时间等，SERVFAIL 换下一台，NXDOMAIN 算失败；超时算「未检测」，不升状态；`makeCheck` 兜了 panic。域名、选择器、TXT 记录的解析函数拿 40 万条随机和变异的输入跑过，不 panic。
- 默认域至多一个由库保证，第一个域自动成为默认域，默认域不能停用、不能删；切换默认域在一个事务里按主键升序加锁。域下还有邮箱或别名时不能删。
- 保留地址设置时两项都要给、目标必须存在、不能指向本域自己的保留地址。

**黑白名单和全局设置**
- 逐项校验（小写、长度、域名或地址的形态）；和另一张名单的重复会拒绝并点名；渲染进 Rspamd 映射文件时拒绝空白、控制字符和 `#` 开头的条目——换行进不去。白名单每分钟对账一次，渲染失败会自愈。
- 联动校验按改完之后的值做（三个阈值的大小关系、附件合计乘 4/3 不超过单封上限），一批里同时抬高两条线能过；任何一项不合法整批不写；改完立即生效（读的是内存镜像）。
- `SettingsApplier` 失败只出告警，不让保存失败；关灰名单是另写一份 `greylist.conf`（`enabled = false;`），开着时删掉它，`actions.conf` 里 `greylist` 这一项照写，没有写成 null；在线改阈值走 `/saveactions`，控制接口关不掉灰名单这件事在 `warnings` 里说清楚了。

**出站限额和策略服务**
- 两个窗口：整点对齐的小时窗口和 UTC 零点对齐的天窗口，各留当前和上一个，上一个按剩余比例折算；判断和累加在同一把锁里。
- 未认证的请求回 DUNNO，不计出站额度；内部出错、判定超时、过载、判定器 panic 都回 DUNNO，并计一次 `PassOnError`（告警和指标从这里取）、记一行告警——任务书里的「并计数」指的是这个统计数，账号都查不到时也没有账号可以计出站额度。
- 时限：读 1 秒 + 判定 2 秒 + 写 1 秒，短于 Postfix 的 5 秒；判定器不理会取消、过了时限才回的结果不采信。
- 来源地址校验：支持单地址和网段，IPv4 映射的 IPv6 按 IPv4 算，网段主机位不为零直接报错，名单外的连接不应答直接断开（逻辑正确；缺省值的问题见丙-10）。
- HTTP 发信和策略服务是同一个 `outbound.Service`、同一组计数器（装配里 `deps.X.Outbound` 就是交给策略服务的那个对象）。默认值和覆盖值每次判定都重新读。

**日志采集**
- 断点：文件标识取首行摘要；重启时核对「文件在、位置上那一行对得上」才接着读，对不上、文件没了、断点没了都从头读，靠去重键（源 + 文件标识 + 偏移 + 行内容）上的唯一索引不重复；轮转是改名式的，按标识找得到改了名的旧文件，旧文件读完才读新文件；接着读之前往回读一段重建归并状态。仓库里的重启、轮转、断点被删、位置对不上、半截行这些用例都在，全过。
- 解析不了的行：计数，连着 100 行算一次异常给告警用。两个解析器和归并流程拿 30 万条随机和变异的行跑过，不 panic（采集器的常驻循环里没有兜 panic，一处 panic 就是整个进程退出，所以专门跑了这一项）。
- 主账号登录的识别见第 2 节。按队列标识归并、10 分钟没有结果收尾成「重试中」；写进表里的每个字段都按列宽截断（超宽字段不会让整批插入失败，在 MySQL 严格模式上试过）。
- 保留期清理：投递、登录、评分、审计四张表，各按自己的设置，5000 行一批、最多 200 批，一张表出错不影响其余。

**对账**：期望集合按范围取；IAM 里查不到的不动；单条失败不影响其余；每轮写运行记录；手动触发立即返回、后台跑、同一时刻只跑一轮；按组织的范围在当前平台用不了时的行为是文档里写明的判断（见第 4 节）。

**配置渲染**
- 注入：数据库口令限定字符集（三处配置文件都能原样表示）；数据库主机、库名、主账号用户名、允许登录的网段各有白名单；域名、选择器、私钥路径（不能逃出密钥目录）、白名单条目都先校验；值里不许有换行、空字节、模板分隔符；渲染结果里不许残留占位符。表示不了的输入一律拒绝，不悄悄写坏文件。
- 原子写入：同目录临时文件（O_EXCL，0600）→ 写入 → 改权限位 → fsync → 改名 → 同步目录；内容和权限位都没变不重写（主账号口令文件不会因为重启而被 Dovecot 重读一遍）。
- 内嵌模板和 `deploy/` 的原件：两个目录逐字节相同（`diff -rq` 无差异），仓库里有同步测试守着。
- `/ping` 挂在 HTTP 入口上，HTTP 是最后启动的组件，排在启动钩子（全量渲染）之后；渲染失败则启动失败，不会带着半套配置去应答。
- 证书变化检查只读证书文件（`cert.go` 的 `certDigest`），不碰私钥；证书和私钥成不成对由运维代理的 `reload.postfix` 去核。

**装配、迁移**
- 接缝顺序：配置渲染 → 账号与域名 → 投递与运维 → 成员邮箱 → `linkAll` → 启动钩子 → 定时任务 → 常驻组件 → RPC → 回环连接 → HTTP。停机反序：HTTP、RPC 先停，日志采集和策略服务次之，批量任务的后台执行排在关出站连接之前。
- `-check-config`：和正常启动同一个加载和校验，出口在开库之前；实跑确认不连库、不落文件、输出不带口令。
- 迁移：`golang-migrate`，迁到最新之后 `VerifySchema` 逐表比对模型和库的列与索引名，对不上就不启动；迁移脚本和模型的逐表对拍有测试（24 张表、8 个视图、down 脚本齐全）；MySQL 真机上的「空库迁到最新、重复迁移、回滚、再迁移」和 README 的建账号语句都跑过，通过。
- 全量 `go build` / `go vet` / `go test -p 2 ./...` 在导出副本里全绿。
