# Claude Code · PPB 邮件域实施

这是邮件域的实施入口。当前状态：设计文档 v0.2 草案已写好，没有评审；代码一行未写；数据库脚本只在一次性的 MySQL 容器里验证过。用户在本地指示开始实施之后，按以下范围推进，并把真实进度写进 [实施进度](PROGRESS.md)。

## 开始之前必须成立的事

四条都成立才开始写代码。缺哪一条，就先把那一条补上，或者停下来问。

1. 用户明确说了开始实施，并且指明做哪个阶段。
2. 这个阶段用到的待确认项，在 [PRD](../PRD.md) 第 11 节里已经有了答复，并且写回了 PRD。M0 只需要第 6 项。
3. 这个阶段的逐任务计划已经生成在本目录的 plans 子目录里，用户看过。计划还没有时，先为这个阶段生成计划并交给用户确认，不直接写代码。生成的办法用 superpowers:writing-plans，输入是本域的 PRD、对应的规则细则和技术设计。
4. 技术设计里“实现时要核对的事项”，与本阶段有关的已经核对完并有结论。M1 自己包含核对，是例外。

## 工作区和授权边界

涉及的仓库和各自的角色：

| 仓库 | 角色 |
|---|---|
| ppb-mail | 新建。控制面服务、契约、管理端插件、镜像和编排 |
| ppb-docs | 本域的全部文档、计划、进度、证据 |
| ppb-iam | M0 的通知邮件修复；M4 新增一个内部接口和权限登记 |
| ppb-chat | M0 的推送记录页 |
| ppb-base | 路由清单、启动脚本、平台门户、要清理的旧文件 |
| ppb-gateway | M3 的流式直转车道 |
| ppb-file | M5 清理死配置 |

规则：

- 先读用户这次给的指令，再读各仓库适用的 CLAUDE.md、AGENTS.md、.claude/rules 和 README。
- 动手前先盘点：每个仓库的远程、分支、HEAD、工作区状态。结果写进实施进度。
- 保留工作区里已有的修改，尤其是别人的在途改动。有冲突时用隔离的 worktree。
- 分支：ppb-mail 里用 feat/mail-m<n>-<主题>；M0 在 ppb-iam 和 ppb-chat 里用 fix/notify-mail-gaps；其他仓库的改动用 feat/mail-m<n>-<主题>。
- 小步提交到各自仓库的实施分支。先在实施分支上验证完，再问用户要不要合并和推送。
- 未经用户本次授权，不做这些：合并到 main；推送到共享分支；创建远程仓库；对公网开放端口；修改 DNS；操作生产环境；执行破坏性的 SQL。
- 工作区里已经有一个空的 ppb-mail/ui 目录，不是本设计创建的。在用户说明用途之前，不删除它，也不在它里面放东西。
- 本地 go.work 只是开发便利。正式的构建和测试关闭工作区。

## 每个任务怎么做

1. 读计划里这个任务的说明，确认它依赖的前序产出都在。
2. 先写失败的测试，运行它，确认它是因为功能还不存在而失败。
3. 写刚好让测试通过的实现。
4. 跑这个任务涉及的全部测试，再跑所在模块的全部测试。
5. 对照计划里的预期结果逐条核对实际输出。
6. 提交。提交信息用 conventional commits，一个任务一个或几个提交。
7. 在实施进度里记一行。

贯穿所有任务的规定：

- **测试针对行为。** 测的是用户和调用方能观察到的结果，不是内部实现。能用真实组件就用真实组件：数据库用测试库，邮件组件用开发编排里跑起来的实例。
- **邮件组件的配置不凭记忆写。** Postfix、Dovecot、Rspamd 的每一项配置，都要在开发编排里实际跑过、用命令验证过效果。
- **契约的改动有固定顺序**：改 proto，重新生成，改契约 JSON，改 Go 访问器，更新契约测试。生成产物和 proto 放在同一个提交里。重新生成之后 git diff 应该为空。
- **数据库只增不改。** 每次变更有 up 和 down 两个脚本。改了 schema.sql 就重跑 `bash tech/sql/verify/run.sh`。
- **秘密不落地。** 凭据只经环境变量或挂载的密钥文件进来。提交前逐个看 diff，确认没有凭据、真实邮箱地址、真实域名、运行数据。
- **文档是契约。** 实现和设计对不上时，不悄悄按自己的理解做。把发现写进实施进度的“核对结论”，改掉技术设计里对应的段落。如果这个发现改变了产品行为或者待确认项的答案，停下来问用户。
- **没做的验证不写通过。** 验收条目的状态只能靠证据改。证据放在 mail/ac/evidence 对应阶段的文件夹里，文件名以验收条目编号开头。

## 检查命令

按模块分别跑。Go 这边有三个模块：contracts-mail 下的生成代码模块、Kitex 桩模块、service-mail。

```bash
# Go 模块，在每个模块的目录里
GOWORK=off go build ./... && GOWORK=off go vet ./... && GOWORK=off go test ./...

# SQL 基线，在 ppb-docs/mail/tech/sql 下
bash verify/run.sh

# 管理端插件，在 mail-manage-web 下
npm run typecheck && npm test && npm run build

# 脚本
bash -n <脚本>

# 文档的静态检查，在 ppb-docs/mail 下
python3 -I tools/check_docs.py .
```

契约漂移的检查：在 contracts-mail 下重新生成，然后 `git diff --exit-code`。

文档改完要跑上面的静态检查。它查的是链接、编号引用、章节号和表格，通过只说明没有这类错误，不说明写得对。

本机的环境注记，来自架构改造时的记录：

- Go 1.26 在 ~/sdk/go1.26.0/bin 下，可能不在 PATH 里，要先加进 PATH。
- 私有模块要设 GOPRIVATE=github.com/maibanku/*,github.com/ppbchat/*。
- 前端的类型检查要用 Node 24。用更新的 Node 会出现假的类型错误。
- 本机的代理会劫持对 127.0.0.1 的请求。跑本地的服务之前，清掉 HTTP_PROXY、HTTPS_PROXY、ALL_PROXY，或者设 NO_PROXY。

## 各阶段要特别记住的

**M0 通知邮件缺口**

- 全部按 [缺口修复设计](../tech/11-通知邮件缺口修复设计.md) 做。九项修复，九个提交，提交的顺序照设计里第 13 节。
- 对外的成功行为不变。推送记录接口只增加一个字段和一个筛选参数。
- 做完之后，把规则细则里对应条目的状态改成“已修复，待上线验证”，并把验收条目的证据栏填上测试名。

**M1 工程骨架**

- 技术核对是这个阶段最重要的产出。每一项都要动手试，结论写回对应技术设计的核对清单，实施进度里也有汇总。
- 新仓库建好之后，先让一个空的服务能通过 -check-config 的正控和负控，能独立构建和测试，再往后做。
- 页面和业务逻辑都不做。

**M2 收发主干**

- 公网实测需要域名、服务器和 DNS 的控制权。没有拿到之前，把本机能做的部分做完：开发编排里的收发、视图的验证、负向检查。
- 开放中继的检查是必过项，不能用“应该不会被中继”代替实测。
- 在这之后每个阶段动到 Postfix 或 Dovecot 的配置，都要重跑一遍 M2 的收发验证。

**M3 成员接口**

- 先做技术验证，选定库，量出性能，再写业务代码。
- 流式车道是 ppb-gateway 和 ppb-base 的改动。在它们合入之前，流式的三个接口只能用接口测试覆盖，不能标成已验收。
- 每一个读操作都要验证它不改变已读状态。

**M4 账号同步与管理端**

- 对账任务必须可以重复执行。写测试覆盖“上一轮跑到一半中断，再跑一轮”。
- 管理端的每一个页面走查一遍，并且确认没有对应权限时被拒。
- IAM 里应用、权限点、菜单的登记方式先核对清楚再动手。

**M5 加固与运维**

- 备份恢复必须真的演练：备份出来，恢复到一个隔离的环境，核对邮件数量。
- 旧残留的清理跨几个仓库，每个仓库单独提改动。删除之前先确认没有依赖。

## 停下来问用户的情形

只有下面这些情况停下来问。其他情况自己判断，把判断和理由记进实施进度。

- 要做不可逆或有破坏性的操作：删除数据、删除目录、执行不可回滚的迁移。
- 要动外部的东西：对公网开放端口、改 DNS、购买或开通服务、往生产环境发邮件。
- 要合并到 main、推送到共享分支，或者创建远程仓库。
- 发现某个设计点不成立，而且改动它会影响产品行为、数据结构或者别的仓库。
- 一个待确认项到了必须用的时候还没有答案。
- 需要的访问权限、服务器、域名拿不到。

## 实施进度怎么记

写在 [实施进度](PROGRESS.md) 里，不另建文件。每一处记录都要能让一个没看过这次会话的人接上：

| 记什么 | 什么时候记 | 内容 |
|---|---|---|
| 基线 | 每个阶段开始时 | 各仓库的分支和 HEAD；工作区状态；工具版本 |
| 任务结果 | 每个任务做完时 | 任务编号；分支和提交；跑了哪些检查命令，结果是什么；证据文件的路径；遗留 |
| 核对结论 | 每核对完一项时 | 原来的问题；结论；改了哪份文档的哪一节 |
| 自己做的判断 | 做判断的时候 | 判断的内容；理由；如果判断错了会有什么后果 |
| 验收门 | 每个阶段结束时 | 哪些条目通过、哪些没有、证据在哪 |
| 待用户决定的事 | 出现时 | 是什么事；卡住了哪个任务 |

一行任务记录的写法：`M2-07 完成，分支 feat/mail-m2-core，提交 a1b2c3d，检查 go test ./... 通过，证据 ac/evidence/M2/MAC-21-inbound-550.txt，遗留 无`。

## 阶段报告

一个阶段做完，或者中途停下来，向用户报告这些内容：

- 做完的任务，涉及的仓库、分支和提交。
- 实际跑过的检查命令和结果。没跑的写明没跑。
- 验收门的结果：通过的条目、没通过的条目和原因、没有证据的条目。
- 核对结论：哪些设计点被确认，哪些被改了。
- 自己做的判断，按做的顺序列出来，每条附上判断错了的后果。
- 阻塞和需要用户决定的事。
- 下一步。

当前的数据、接口和运行行为与文档有矛盾时，先列出证据和影响范围，然后继续做不依赖这个矛盾的工作。
