> v0.3。契约已经落地在 ppb-mail/contracts-mail（2026-11-25），路由清单、网关车道和 IAM 里的登记也已落地，都还在各仓的分支上，没有合入。字段的事实来源是契约的 proto；落地时和 v0.2 草案不一致的地方已经在本文改过来，见版本表的末行。规则来源：[成员接口](../pr/05-成员接口.md)、[管理端](../pr/06-管理端.md)。实现思路见 [成员接口设计](06-成员接口设计.md)、[管理端设计](07-管理端设计.md)。

## 1. 契约怎么落地

沿用平台现有做法，不另起一套：

| 内容 | 位置 | 说明 |
|---|---|---|
| 消息和 RPC | ppb-mail/contracts-mail/proto/mail.proto | 包名 mail。消息和 RPC 都定义在这里，由工具生成 Go 代码 |
| HTTP 路由 | ppb-mail/contracts-mail/api/mail-member-http.json、mail-manage-http.json、mail-public-http.json；流式接口写在同目录的 streaming-routes.md | 每条路由绑定到一个 RPC 方法和一对请求响应消息，路径参数和查询参数显式绑定到请求字段。第三份是匿名路由，目前只有转发地址确认一个操作。四个流式接口不进契约 JSON，由服务里的手写处理器承接 |
| Go 访问器 | ppb-mail/service-mail/api/contracts.go | 内嵌上面三份 JSON，交给平台的契约解析器校验 |
| 契约测试 | ppb-mail/service-mail/api/contracts_test.go | 断言路由条数、路径前缀、权限字段，防止契约和实现漂移 |
| 网关策略清单 | ppb-mail/api/policies/mail.yaml | 每个操作一条治理数据 |
| 网关路由清单 | ppb-base/deploy/route-manifest.yaml | 增加一个 mail 条目，指向上面三份 JSON；gateway 条目的 specials 里加三条 mail 车道，见第 7 节 |

JSON 契约按 file 和 camera 的最新做法放在 contracts-mail/api，是唯一的归属地。照抄的对象是 ppb-file/contracts-file/api 和 ppb-file/service-file/api。

RPC 分两个服务，不合并成一个：

| 服务 | 面向 | 路径前缀 |
|---|---|---|
| mail.MailboxService | 成员 | /api/v1/mail |
| mail.MailAdminService | 管理端 | /api/v1/manage/mail |

分开的原因是 FP-G18：管理面的代码不能依赖访问邮箱的能力。两个服务的处理代码放在不同的包里，有一个依赖方向测试锁住，见第 7 节。

本期不提供内部 RPC。其他服务目前没有调用邮件服务的需求，等有了再加，不预先设计。

## 2. 通用约定

### 2.1 响应信封

沿用平台统一信封。字段名用小驼峰。

```json
{"code": 0, "success": true, "message": "ok", "data": {"page": 1}}
```

```json
{"code": "MAIL-1013", "success": false, "message": "邮件不存在或无权访问", "data": null}
```

失败时 HTTP 状态码取错误码对应的状态，见第 6 节。流式下载和导出文件不套信封。转发地址确认接口返回的也是信封：结果页由网页客户端拿它的结果渲染（网页客户端的路由是 /mail/forward/verify），确认信里的链接指向那一个。

### 2.2 数据类型

| 类别 | 约定 |
|---|---|
| 标识 | 字符串。数据库主键按十进制字符串传输；邮件、文件夹、附件的标识是带签名的不透明字符串，见 3.1 |
| 时间 | RFC3339 格式的 UTC 时间，例如 2026-11-24T08:00:00Z |
| 枚举 | 数值，取值写在契约注释里。proto 里用 int32，不用 enum |
| 分页 | 请求 page、pageSize；响应 total、page、pageSize。成员接口默认每页 50 条，管理接口默认 20 条，上限都是 100 条。超出上限的值回退为默认值 |
| 空值 | 列表字段没有数据时给空数组，不给 null；零值不省略。为此三份契约都打开了 `emitUnpopulated`，它需要一个连带约定，见下一行 |
| 数值 | 64 位整数在 JSON 里是十进制字符串。所以字节数分两档：邮件、附件、队列项、日志行这类不会很大的用 32 位整数，按数值传输；配额和磁盘用量用 64 位整数，按字符串传输 |
| 查询里的布尔筛选 | URL 查询参数只能绑定字符串和正整数，所以布尔筛选写成 1 或 0：1 是只要这一类，0 是不限 |
| 邮箱地址 | 传输时转小写；带显示名的用地址对象，见 3.2 |

管理接口的时间范围筛选沿用平台的写法：查询参数名是 startTime、endTime（unix 秒，含端点），绑定到请求字段 startTimeUnix、endTimeUnix。成员接口的时间参数一律 RFC3339。

### 2.3 身份

| 面 | 登录态 | 操作者字段 |
|---|---|---|
| 成员 | 平台成员登录态。由网关的成员门校验后转给控制面，控制面按平台的服务认证组件再校验一次 | operatorId，由网关从登录凭据注入，值是成员标识。客户端在请求体里带的值一律覆盖 |
| 管理 | 平台管理端登录态。网关做权限前判，控制面复检 | operatorId，值是管理员用户标识，同样由网关注入 |

成员登录态的主体是组织内的成员标识，邮箱账号对应的是 IAM 用户标识，两者不是同一个量。控制面的处理顺序：

1. 从请求上下文取成员标识。
2. 调 IM 的 `ResolveMemberIds`，把成员标识换成用户标识（不能用名字相近的 `ResolveMembersByIds`，它按用户标识查，方向是反的）。结果放进进程内缓存，有效期 5 分钟，上限 10 万条；查不到的结果缓存 30 秒。成员被移出组织后，登录态本身会失效，所以缓存不额外处理这种情况。
3. 用用户标识查邮箱账号。查不到，或账号不是正常状态，返回 403 和 MAIL-2001（A00-6）。

成员标识换用户标识这一步失败时返回 503，不放行。

### 2.4 幂等

发送接口的幂等键放在请求体的 idempotencyKey 字段里，长度 1 到 128 个字符。契约处理器读不到请求头，所以不放在请求头里。实现时没有做对请求头 Idempotency-Key 的兼容（整仓评审时确认）：只认请求体里的这一个字段，客户端不带它时按参数错误处理（MAIL-1001），不会静默重复发送。规则见 A09-3，实现见 [成员接口设计](06-成员接口设计.md) 6.2。其他成员写操作是天然的幂等操作（设置类是覆盖，批量操作按邮件标识），不要求这个键。

### 2.5 限速与大小

每用户限速，见 X07-2：读接口每分钟 300 次，写接口每分钟 60 次，附件上传每分钟 30 次。超限返回 429、MAIL-4291，响应头 Retry-After 给出等待秒数。限速计数在控制面内存里，单实例部署下够用。

JSON 请求体上限 1 MB，超出返回 413、MAIL-1016。附件上传的单文件上限见 A08-2。

### 2.6 流式接口

四个接口不走 JSON 信封，经网关的流式直转车道到控制面：

| 接口 | 方向 | 内容 |
|---|---|---|
| POST /api/v1/mail/attachments | 上传 | multipart 表单，文件字段名 file。响应仍是 JSON 信封 |
| GET /api/v1/mail/messages/{messageId}/attachments/{attachmentId} | 下载 | 附件字节流 |
| GET /api/v1/mail/messages/{messageId}/raw | 下载 | 整封邮件，.eml |
| GET /api/v1/manage/mail/logs/delivery/export | 下载 | 投递日志，CSV |

下载的响应头固定三项：Content-Type 为 application/octet-stream，Content-Disposition 为 attachment 并且文件名按标准方式编码，X-Content-Type-Options 为 nosniff（A05-1、A05-4）。流式车道上同样要过身份校验和权限前判，见第 7 节。

## 3. 成员接口

服务 mail.MailboxService，前缀 /api/v1/mail，身份 member。下表的 RPC 省略服务前缀。

### 3.1 标识的格式

| 标识 | 格式 | 内容 |
|---|---|---|
| 邮件标识 | m.负载.签名 | 版本、邮箱账号主键、文件夹有效性标识、邮件编号、UTF-8 文件夹名 |
| 文件夹标识 | f.负载.签名 | 版本、邮箱账号主键、UTF-8 文件夹名 |
| 附件标识 | a.负载.签名 | 邮件标识的全部内容，再加邮件里该部分的位置 |
| 会话标识 | 一个邮件标识 | 会话里最早那封邮件的标识 |

- 负载的各段用点分隔，文件夹名和部分位置先做 base64url 编码。负载和签名本身也做 base64url 编码，不带填充，可以安全地放进网址路径。
- 签名是 HMAC-SHA256，密钥来自环境变量 MAIL_HANDLE_SECRET，取前 16 字节。
- 校验时先验签名，再比对负载里的邮箱账号主键和当前用户的账号是否一致。任何一步不过都返回 404 和 MAIL-1013，不区分“不存在”和“不是你的”（A18-2）。
- 文件夹重建后有效性标识变化，旧邮件标识失效，同样返回 404（见 [成员接口设计](06-成员接口设计.md) 3.1）。
- 密钥轮换后旧标识全部失效，客户端重新拉列表即可。轮换选在低峰时间做。

### 3.2 公共数据结构

| 结构 | 字段 |
|---|---|
| Address | name（显示名，可空）、address |
| Folder | folderId、name、parentId（顶层为空）、specialUse、totalCount、unreadCount |
| AttachmentInfo | attachmentId、fileName、mimeType、size、contentId（正文内嵌图片才有值，A04-6） |
| MessageSummary | messageId、threadId、subject、from（Address）、date、unread、starred、hasAttachment、size、preview、folderId |
| MessageDetail | MessageSummary 的全部字段，加 to、cc、bcc（Address 数组）、textBody、htmlBody、attachments（AttachmentInfo 数组） |
| BatchResult | succeeded（数量）、failed（数组，元素为 messageId、code、message） |

Folder.specialUse 取值：0 普通；1 收件箱；2 已发送；3 草稿；4 已删除；5 垃圾邮件。五个标准文件夹的 name 固定为 INBOX、Sent、Drafts、Trash、Junk。

### 3.4 请求与响应要点

**概览与文件夹**

| RPC | 请求 | 响应 data |
|---|---|---|
| GetOverview | 无 | folders（Folder 数组，A01-1）；quota：usedBytes、limitBytes（A01-2）；address（主地址）；aliases（SelfAlias 数组，A01-3：aliasId、aliasAddress、source——1 管理员添加、2 用户自助添加、3 修改主地址后保留的旧地址——deletable，只有来源是用户自助的才为真，A19-3）；displayName、avatarUrl（A01-4）；outboundAllowed；initialPasswordRequired（没有可用密码时为真：自动开通后还没设置，或临时密码已过期，A16-2）。界面上身份的写法见 [域导航](../README.md) 的界面约定 |
| ListFolders | 无 | folders |
| CreateFolder | name、parentId（空表示顶层；最多两层，A02-3） | folder |
| RenameFolder | name | folder |
| DeleteFolder | 无。文件夹非空时返回 409 和 MAIL-1009，并带上邮件数（A02-5） | 空 |

**列表与读**

| RPC | 请求 | 响应 data |
|---|---|---|
| ListMessages | 路径 folderId；查询 page、pageSize、unreadOnly、starredOnly、hasAttachment、since、until（时间范围，两端都含） | items（MessageSummary 数组）、total、page、pageSize |
| SearchMessages | 查询 q（必填，1 到 200 个字符）、folderId（可选，不传为除草稿外的全部文件夹）、其余筛选和分页同上 | 同上，另带 costMs 供排障 |
| GetMessage | 路径 messageId | message（MessageDetail） |
| DownloadAttachment、DownloadRaw | 路径参数 | 字节流 |

读别人发来的邮件时，bcc 只保留本人那一个地址；读自己发出的邮件时全部返回（A04-5）。

**发送与草稿**

写邮件类请求的公共字段（发送和保存草稿共用）：

| 字段 | 说明 |
|---|---|
| mode | 1 新邮件；2 回复；3 全部回复；4 转发 |
| sourceMessageId | mode 为 2、3、4 时必填，是原邮件的标识 |
| fromAddress | 可空，空则用主地址；必须是本人的主地址或别名（A06-6） |
| to、cc、bcc | Address 数组 |
| subject | 最长 256 个字符 |
| textBody、htmlBody | 纯文本必填；HTML 可空 |
| attachmentIds | 暂存附件标识数组 |

| RPC | 请求 | 响应 data | 失败 |
|---|---|---|---|
| SendMessage | 上述字段，加请求体字段 idempotencyKey（请求头 Idempotency-Key 也兼容，请求体里有值时以请求体为准） | messageId（已发送副本的标识）、messageIdHeader（邮件追踪号）、threadId、submittedAt、recipientCount | 见下表 |
| SaveDraft | 上述字段；收件人和主题可空（A07-1） | messageId（草稿标识） | 同成员接口通用错误 |
| UpdateDraft | 路径 messageId 是草稿标识；请求体同 SaveDraft | messageId（新草稿的标识，旧草稿被替换） | 草稿不存在 404 |

草稿是草稿文件夹里的普通邮件：列出和读取用列表接口和读接口，指定草稿文件夹。删除草稿用 TrashMessages。从草稿发送成功后，这份草稿被删除（A07-4）。

SendMessage 的校验顺序和对应错误见 [成员接口设计](06-成员接口设计.md) 6.2。

回复和全部回复的收件人由客户端填写，服务端只负责写回复关联头和主题前缀（A06-2、A06-3）。按原邮件推导收件人的规则写在契约注释里，供客户端实现；服务端在收件人为空且 mode 为 2 或 3 时返回 400。

**暂存附件**

| RPC | 请求 | 响应 data |
|---|---|---|
| UploadAttachment | multipart，字段 file | attachmentId、fileName、mimeType、size、expireAt |

**投递状态**

| RPC | 响应 data |
|---|---|
| GetDeliveryStatus | messageIdHeader；recipients 数组，元素为 address、status、reason、time；refreshedAt |

status 取值：1 已投递；2 投递中；3 已退信（A10-1）。messageId 必须是本人已发送文件夹里的邮件，否则 404（A10-3）。

**标记与移动**

| RPC | 请求 | 说明 |
|---|---|---|
| SetMessageFlags | messageIds、unread、starred | unread 和 starred 是三态的：不带表示不改，带 true 或 false 才改；两个都不带返回 400 |
| MoveMessages、CopyMessages | messageIds、targetFolderId | 目标是已删除文件夹时等同 TrashMessages |
| TrashMessages | messageIds | 移到已删除，并记录原文件夹 |
| RestoreMessages | messageIds | 只对已删除文件夹里的邮件有效 |
| PurgeMessages | messageIds、permanent | permanent 必须为 true，否则 400（A12-4）；只对已删除文件夹里的邮件有效 |

四个批量接口的 messageIds 上限都是 500（A11-2、A12-1），响应都是 BatchResult，部分失败时整体返回 200，失败明细在 BatchResult 里（A11-3、A12-6）。

**设置**

| RPC | 请求 | 响应 data |
|---|---|---|
| GetAutoreply | 无 | enabled、startAt、endAt、subject、body |
| SetAutoreply | 同上 | 同上 |
| GetForward | 无 | forwardAddress、keepCopy、enabled、verifyStatus、verifyExpiresAt |
| SetForward | forwardAddress、keepCopy | 同上。每次修改目标地址都要重新验证 |
| DeleteForward | 无 | 空 |
| ResendForwardVerification | 无 | verifyStatus、verifyExpiresAt |
| VerifyForward | 查询 token | 和其他接口一样套 JSON 信封，成功时 data 里只有 base。确认成功或失败的页面由网页客户端拿这个结果来渲染 |

- 自动回复的字段约束见 S16：正文纯文本，不超过 5000 字；结束时间早于开始时间返回 400。
- 转发的令牌 48 小时有效，只能用一次（A14-4）。令牌无效、过期或已使用时，页面显示失败原因，状态码 400。
- 管理员关闭了用户自助转发时，SetForward 和 ResendForwardVerification 返回 403 和 MAIL-2005（A14-5）。
- 自动回复和过滤规则修改后都要经脚本编译，编译不过返回 400 和 MAIL-1012，原有设置保持不变（A15-3）。

**过滤规则**

一条规则的结构：

| 字段 | 取值 |
|---|---|
| ruleId、name、enabled、order | 标识、名称（最长 64 个字符）、是否启用、执行顺序 |
| conditions | 数组。每个元素：field（1 发件人；2 收件人；3 主题）、op（固定为 1，包含）、value |
| sizeOverBytes | 可空。有值时追加“邮件大小超过”这个条件 |
| action | type：1 移动到文件夹；2 标星；3 标为已读；4 转发到地址；5 删除。targetFolderId 在 type 为 1 时必填；forwardAddress 在 type 为 4 时必填 |

- 条件之间是“并且”关系（S17-2）。每条规则一个动作；要多个动作就写多条规则。
- 至少要有一个条件。每个用户最多 50 条规则（S17-1）。
| RPC | 请求 | 响应 data |
|---|---|---|
| ListFilterRules | 无 | rules，按 order 升序 |
| CreateFilterRule | name、enabled、conditions、sizeOverBytes、action；order 可空，空则排到最后 | rule |
| UpdateFilterRule | 同上 | rule |
| DeleteFilterRule | 无 | 空 |
| ReorderFilterRules | ruleIds，按新顺序排列，必须包含全部规则 | rules |

ListAuditLogs 的每一行：adminUserId、adminName、actionCode、targetType、targetId、targetLabel、before、after、clientIp、result、createTime（G15-1）。

### 4.4 管理接口的权限复检与审计

1. 网关按契约里的权限对象做前判。
2. 控制面收到请求后，对每个操作向 IAM 复检操作者的管理权限。做法参照 service-file 对 IAM 授权接口的包装。
3. 复检不通过返回 403 和 MAIL-2101。
4. 写操作按 [管理端设计](07-管理端设计.md) 第 12 节的规则记审计。审计由处理器自己记：契约里声明的审计信息不够（不记变更前后的值，失败时只告警），装配时把契约处理器自带的审计接成空的，免得记两份。

```yaml
    source: ../ppb-mail/service-mail

      - ../ppb-mail/contracts-mail/api/mail-member-http.json
      - ../ppb-mail/contracts-mail/api/mail-manage-http.json
      - ../ppb-mail/contracts-mail/api/mail-public-http.json

  # gateway 条目的 specials 里追加三条
  - { key: mail_transfer, upstream: mail, comment: /api/v1/mail/* 整段直转 }
  - { key: mail_manage_export, upstream: mail, comment: /api/v1/manage/mail/logs/delivery/export 投递日志导出 }
  - { key: mail_manage_bridge, upstream: iam, comment: /iam/api/v1/business/manage/mail/* 经 IAM 业务桥，时限取 mail 上游的 }
```

原有的 mail 条目写的是 enabled: false 和“外部独立部署”，要改掉。改完后用平台的生成工具重新生成 deploy/config/gateway-routes.yaml，生成失败说明契约或路径有冲突。生成器把 specials 的键名原样渲染、不校验，键名拼错等于没加车道，所以清单测试里把每条车道的键名和指向上游钉死。

流式直转车道照 file_transfer 的先例做，邮件有三条：

- `mail_transfer`：`/api/v1/mail/` 整段直转到 mail 上游，承接附件上传、附件下载和原邮件下载。契约里的精确路由更具体，优先匹配，不受影响。
- `mail_manage_export`：只承接 `/api/v1/manage/mail/logs/delivery/export` 一个路径。它在管理前缀下，整段直转覆盖不到。
- `mail_manage_bridge`：管理端门户带 Cookie 访问邮件管理面时，请求走 IAM 的业务桥（`/iam/api/v1/business/manage/mail/*`），由 IAM 转给控制面。请求仍发往 IAM，但网关等响应头的时限取 mail 上游的（120 秒）：IAM 的桥要等控制面回完才应答，一轮 DNS 校验最长 60 秒，按 IAM 自己的 3 秒会掐断。

车道只做转发，身份校验和权限判定都在上游做：成员面由控制面的成员门校验登录态，管理面由 IAM 的桥和控制面复检权限。

合入顺序是先网关、后路由清单。清单里出现网关还不认识的车道键时，车道不生效，那一段落回原来的路径。

依赖方向测试：用 go list 取管理面处理代码所在包的传递依赖，断言其中没有 IMAP 访问包和邮件读写包（G18-4）。

2026-11-25 到 26 实现控制面、网页客户端和管理端插件的时候发现的。**契约都没改**，每一处现在的做法写在表里；要不要改契约，见 [PRD](../PRD.md) 第 11 节。

|---|---|---|---|
| C-01 | 概览的别名只给地址字符串，而删除别名按标识删 | 已改：概览的别名带标识、来源和能否删除（`SelfAlias`），契约修正 787e37e | 无 |
| C-02 | 概览没有「邮箱有没有可用密码」，客户端不知道该给「设置初始密码」还是「修改密码」 | 已改：概览加 `initialPasswordRequired`（同上） | 无 |
