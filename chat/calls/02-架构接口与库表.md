# 架构、接口与库表

## 1. 总体选择

推荐先验证本地部署LiveKit SFU及其独立Egress录制服务，复用已有MySQL/Redis、MQ与文件平台；信令与业务状态由PPB管理，音视频直接走RTC媒体网络，不经过Gin/gRPC消息转发或现有IM WebSocket。

```text
Vue通话UI → Tauri Rust通话控制 → PPB网关 → server-im通话域
                              ↘ 受限RTC媒体连接 → 本地SFU/TURN
server-im → 房间/参会授权 → SFU
SFU webhook → 验签/去重 → server-im状态投影/WS业务事件
录制服务 → 私有产物 → 文件平台登记/引用 → 后台授权播放
```

依据：LiveKit官方提供自托管、TURN部署及单独部署Egress；Rust SDK提供实时音视频能力。它们是选型依据，不代表已验证Tauri内的完整采集、播放与视频渲染。

- https://docs.livekit.io/transport/self-hosting/
- https://docs.livekit.io/transport/self-hosting/deployment/
- https://docs.livekit.io/transport/media/ingress-egress/egress/
- https://github.com/livekit/rust-sdks

## 2. 原生技术门槛

保留现有原则：业务token不进入WebView、HTTP/WS业务调用经Rust。RTC短期凭证也由Rust获取/持有，限定房间和身份，前端只接收状态、非敏感参与者信息和受控画面句柄。

优先原型验证Rust SDK、设备采集/播放与GPU/原生视频面板渲染。不能将30fps视频逐帧base64经Tauri事件转到Vue。原型需测macOS与Windows、权限、释放设备、多窗口及视频同步。

明确依赖边界：不编写自有C++业务代码，但Rust RTC SDK底层可能包含原生WebRTC/C++依赖，不等同于纯Rust。如果“去除C++”要求包含禁止所有此类依赖，该选型不满足，必须先做ADR。若考虑WebView媒体SDK，也必须先修改架构决策说明凭证/媒体权限边界，不能悄悄绕过现有原生网络规则。

此门槛通过前不铺开客户端实现；未通过时提交两条技术路线的可运行证据与代价，不能把SDK下载成功当完成。

## 3. 服务边界

先在server-im新增独立call业务包与repo，不立即新建业务微服务。通话域不能继续堆进消息发送函数。

网关只做认证、限流、权限、参数与RPC转发；server-im负责当前会话资格、成员邀请、设备唯一接听、状态迁移和媒体授权。SFU负责媒体传输；Egress负责录制；文件服务负责产物、授权引用及保留。MQ承接完成后登记、转写和对账，不承载音视频帧。

MySQL是业务事实源；Redis处理短期占用锁与路由，不能仅依赖锁判断通话状态。业务事件采用事务outbox或现有可靠投递机制，消费者幂等。供应商回调验签、限流、保存event ID、乱序保护，并有周期性房间/录制任务对账。

## 4. 状态模型

通话：creating→ringing→active→ending→ended；未接通终态分别cancelled/rejected/timeout/failed。终态带明确reason。群内单人的拒绝不能结束所有人的邀请。

参与者：invited→ringing→accepted→joining→joined→left；另有declined/missed/busy。每次重连独立join segment，不能覆盖首次进入时间或重复累计重叠时长。

单聊双方真实媒体加入后才接通；群聊至少两位业务参与者媒体加入后开始有效通话，不将发起者独自在房间内算已接通。实际规则由领域状态机与可信回调裁定。

录制：requested→consent_pending→starting→recording→stopping→processing→ready；另有declined/failed/expired/deleted。webhook完成不等于文件已经入库可播放，文件登记与校验完成后才ready。

## 5. 新增表（规划，未执行DDL）

现有im_message/im_file不足以表达多人实时会话和录制任务，需要通话领域表，媒体文件继续复用文件平台。

| 表 | 核心列与约束 |
|---|---|
| im_call | id/biz_key、conv_id、initiator_member_id、client_request_id、media_mode、status、reason、room_id、started_at/answered_at/ended_at、version；发起人+client_request_id唯一 |
| im_call_participant | call_id/member_id唯一、inviter_id、invite_status、accepted_device_id、ring/accept/reject时间、recording_consent；不把成员每次连接压到一行时间内 |
| im_call_join_segment | call_id/member_id/device_id、媒体participant identity、joined_at/left_at、reason；媒体session identity唯一，开放区间需对账闭合 |
| im_call_event | call_id、事件来源、source_event_id、序号/版本、发生/接收时间、最小事件负载；来源+source_event_id唯一 |
| im_call_recording | biz_key/call_id、egress_id、segment_no、status、file_id、duration_ms/size/mime、started/ended/ready时间、expire_at、error_code；egress_id唯一 |
| im_call_recording_consent | recording_id/member_id唯一、确认设备、accepted/rejected、时间、提示版本；逐次录制留证，不能只保留参与者表的最新布尔值 |
| im_call_transcript（阶段2） | recording_id、任务状态、语言、模型/版本、错误码；重试幂等 |
| im_call_transcript_segment（阶段2） | transcript_id、start_ms/end_ms、文本、可空speaker_member_id、置信度；禁止将未知speaker猜成人员 |

公共列沿用本仓ID、业务键、软删除与时间规范；索引覆盖conv+create_time、status+expire_at、call+member等访问路径。录音原始字节不放MySQL，不在消息正文塞长转写，不增加跨库外键。已有outbox/审计表优先复用。

录制审计是管理员访问行为；call_event是通话事实，不用同一表混存。媒体底层身份必须能映射到PPB成员和设备，不接受前端自报sender身份。

## 6. 接口草案

以下为规划路径，尚不存在；均需Proto和网关契约共同落地，遵守网关治理方案。

- POST /api/v1/im/calls：convBizKey、mediaMode、inviteeBizKeys、clientRequestId、recordingRequested；校验资格、人数、并发通话、好友/群门禁。
- GET /api/v1/im/calls/{callBizKey}：当前调用者有权看到的通话与参会状态。
- POST .../{callBizKey}/accept、reject、cancel、leave、end：明确独立语义与权限，不能由一个不受约束的status参数任意跳转。
- POST .../{callBizKey}/join：当前资格复核并签发短期RTC凭证，仅Rust消费；重连需重新鉴权，退群/移除后拒绝并踢出已有连接。
- POST .../{callBizKey}/recordings：申请新片段；POST .../recordings/{recordingBizKey}/consent、stop。
- GET /api/v1/manage/calls、GET .../{callBizKey}：分页列表和详情。
- GET .../{callBizKey}/recordings；授权播放会话/下载令牌接口独立，发放令牌和实际读流都鉴权，支持Range与过期。
- 内部回调入口：媒体/录制服务验签，不能走普通成员token，也不能无校验放公网白名单。

所有写接口具幂等键/版本校验。浏览器和客户端不传recording对象存储路径，下载参数不能成为任意URL代理。播放内容权限与列表权限分离。

WS仅传call.invited/updated/ended、participant.updated、recording.updated等业务事件；消息总线不同步传SDP/媒体帧。事件带callBizKey、version、eventId，重连后REST取快照再按版本追平。呼叫人名等必须来自服务端。

## 7. 本地部署与配置

在现有deploy/docker-compose.yml之外增加可组合的RTC覆盖文件，固定镜像版本；连接已有Redis、MySQL、MQ、文件存储。自托管录制需要单独Egress服务，不假设SFU容器自动带录音。

按实际开发环境配置可达的媒体IP、UDP/TCP与TURN，不能把容器内部地址或localhost发给其他设备。生产HTTPS/WSS、证书和NAT需单独验证。局域网通话成功不代表外网/TURN可用。

私有产物由录制worker导入文件平台；若Egress采用S3输出，先核实当前文件存储适配能力，必要时使用本地兼容对象存储做中转，不能假设现有文件服务已实现S3协议。

RTC API secret、录制服务凭证通过服务端配置注入，不写进前端、示例截图、日志或Git。端到端加密与服务端录制存在能力边界，本方案不宣称同时具备服务端无法解密的媒体E2EE和服务端可回放录音。
