# 模块边界与服务调用

## 依赖方向

| 层次 | 可以依赖 | 持有的职责 |
|---|---|---|
| go-framework 轻量基础模块 | 标准库及已选轻量基础库 | 日志、请求 ID、错误、生命周期和接口 |
| gRPC、数据库、MQ、Redis 等适配模块 | 基础模块和对应驱动 | 通用连接与传输机制 |
| contracts/common | 必需的协议运行库 | 公共线面类型与兼容类型 |
| contracts/领域 | common 及明确列出的兼容协议 | Proto、生成类型、客户端与服务端接口 |
| platform-sdk/领域 | 本领域契约、必要兼容契约、通用传输模块 | 客户端接入与错误检查 |
| service-* | 按需选择框架、SDK、契约和本业务代码 | 数据、业务规则、状态和操作编排 |

基础框架不反向依赖 contracts、平台 SDK 或业务服务。SDK 之间避免相互引用，由服务启动入口组合多个客户端。RPC handler 的本地业务实现保持在所属服务的 internal 中。

当前 servicehttp 直接依赖 common 与业务 descriptor。迁移时先将协议相关适配留在服务或单独的接入模块，再提取通用绑定机制。不能为满足目录树把协议反向塞回 go-framework。

## 按需使用一个或多个能力

| 使用场景 | 直接依赖示例 |
|---|---|
| 只写结构化日志 | go-framework |
| 日志与 IAM | go-framework、platform-sdk/iam |
| IAM 与文件 | 增加 platform-sdk/file |
| 可靠事件 | 增加 mq/rabbitmq 及 outbox/gorm |
| Redis 缓存或实时路由 | 增加 cache/redis |
| 网关 | 实际使用的通用组件和 HTTP 代理设施 |

按包导入控制编译内容，按 go.mod 控制模块依赖和发布版本。配置开关控制运行时初始化，不能代替构建依赖隔离。禁用某项功能后仍需验证相应接口和数据流程的行为。

## 统一 SDK 规范

IAM 与 File 客户端采用同样的生命周期和方法封装规范。

1. 接收 context 和明确的请求参数，复用启动时创建的连接。
2. 设置操作超时，并传播请求 ID、调用方身份以及经验证的委托上下文。
3. 调用生成客户端，区分网络／gRPC 错误与业务错误。
4. 校验成功回执必需字段。文件登记需核对业务错误码、非零 ID 及其与请求的一致性。
5. 返回可判断的统一错误。会话无效、权限不足和服务不可用分别表达。
6. 自动重试按方法配置，写操作先具备幂等保证。日志不记录密钥或完整凭据。

SDK 只处理接入与响应，消息提交、文件引用确认和失败补偿由业务服务编排。先复用现有实现，避免同时维护原客户端和新 SDK 两套不同规则。

## 请求与端口

以下是源码模板中的默认端口，跨机器地址在部署配置注入。

| 服务 | 客户端经网关访问的 HTTP | 内部 gRPC |
|---|---|---|
| IAM | 9117 | 9107 |
| IM | 9112 | 9102 |
| File | 9114 | 9104 |
| Camera | 9116 | 9106 |

客户端使用 HTTP／OIDC／WebSocket 访问公开入口。业务服务在私网直接调用对应服务，运行时依赖与源码仓库位置分别配置。SDK 和契约编译进消费方，无需单独运行。

网关启动时加载路由表，匹配方法、路径模板或前缀，移除外部 X-Ppb-* 内部身份头，保留业务凭据交给服务校验。它代理 /ws 到 IM，由 IM 校验和管理连接。IAM 管理业务桥当前还会校验 Cookie、生成请求绑定断言，再向业务 HTTP 转发。

当前代理使用 HTTP 上游，服务间 gRPC 使用现有内部凭据机制。跨机部署必须核对私网可达性、凭据、传输保护和允许的调用方。更换 mTLS 或服务身份方案属于单独的安全变更，需新旧链路兼容验证。

## 各业务调用

| 业务 | IAM | File |
|---|---|---|
| Chat | 会话／平台权限和注册供给，组织成员资格归 Chat | 附件上传、元数据和会话引用；File 回调 Chat 裁决业务访问 |
| Camera | IAM 账号登录与 Camera 主体链路分别保持；管理面调用 IAM | 云输入和分析产物的统一文件接入为待实施能力 |
| Wardrobe | 当前自有令牌，统一身份关联需另行设计和验证 | 图片／试穿资源接入需另行设计和验证 |
| IAM | 本地账号和会话逻辑在 IAM 内处理 | 当前管理桥已有 File HTTP 调用；头像等业务 RPC 接入按实际实现核对 |

服务身份与用户身份分别校验。IAM 认证有效不自动授予文件访问，业务服务根据已验证主体、资源归属和应用范围裁决。File 的公共化不能要求所有产品用户先成为 Chat 成员。

## 文件一致性

当前附件发送顺序是登记 File 引用、写 IM 附件、写消息、推送。File 的引用与 IM 的消息分别落库。重复登记和消息去重解决部分重试问题，不能证明跨服务原子性。

SDK 提取需要验证业务失败回执。可靠引用确认采用 [文件接入与一致性](../file/tech/业务接入与一致性.md)中的待确认、业务事务与 Outbox、提交确认、幂等重试、补偿和对账设计。该设计仍需结合当前 ID 线面落实。

File 当前以会话作为一类引用对象，同一会话的多条消息可能共用引用。单条消息失败不能直接删除整个会话引用。待确认引用的 GC 保护与下载资格分别管理，确认前不新增业务读取权限。

## 日志、MQ 和故障隔离

- 普通日志沿用结构化输出，由 Collector 或其他采集器异步采集，采集故障不应阻塞普通请求。
- 业务审计按产品要求可靠写入；不能把普通日志丢弃策略套到关键审计。
- RabbitMQ 作为基础设施部署。业务提交与 Outbox 同库事务，Relay 发布确认后记录投递状态，消费者幂等处理并确认。
- 未启用事件功能时明确关闭相应业务路径。已承诺可靠投递的事件在 Broker 故障时留待重投，不能静默丢弃或切到进程内假成功。
- File 故障影响文件操作；与文件无关的文本功能按实际依赖运行。IAM 不可用时受保护接口按既有安全语义拒绝，公开／本地能力分别判断。
- 可选依赖按功能初始化；启动就绪与故障策略依据核心能力判断，避免日志、可选通知等故障拖垮全部功能。

## 前端公共包和独立应用

| 工程 | 包产物 | 可部署产物 |
|---|---|---|
| base-manage-web | 公共组件、主题、应用工厂、插件契约 | 底座演示与基础验证应用 |
| 各业务 manage-web | 本业务管理插件 | 本业务独立管理端 |
| platform-manage-web | 消费底座和业务插件 | 完整跨应用平台门户 |

底座的库入口输出到 dist/lib，独立入口输出到 dist/app。业务插件装配集中到平台门户，其他独立宿主只装配自己使用的插件。Vue、Router 等共享运行时需要明确 peerDependencies、external 和支持范围，校验单实例与样式导出。

发布版本包后清理 file:、跨仓相对路径、Vite 别名和指向其他工程 src 的导入。目前 package.json 的 private 标记、exports 指向源码、类型声明、CSS 和 npm 权限都需实际发布验证。
