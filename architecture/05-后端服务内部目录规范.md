# PPB 后端服务内部目录规范与迁移说明

> 状态：目标结构与分批迁移清单，尚未执行。本文记录六条业务线的文件落点和验收条件。启动前配置检查已纳入必做项：先做 IAM 试点，再随各服务部署配置迁移推广（第 6.1、7 节）。第 8 节仍是非阻塞的待选增强。
>
> 范围：IAM、IM、File、Camera、Gateway、Wardrobe 六个 Go 服务，以及 `ppb-base` 的共享模块、部署和服务模板。本文决定**服务内部**如何归档；已有仓库归属、Go 模块路径、协议发布方式保持不变。不涉及客户端和管理台目录重排，也不重建已退役的 `server-pkg`。

## 1. 已确定的规则

| 要找什么 | 落点 | 不做什么 |
| --- | --- | --- |
| 程序入口、依赖装配、gRPC 注册、HTTP 路由挂载 | `cmd/<现有入口>/`；Gateway 首轮保留模块根入口 | 不在入口实现登录、上传等业务规则 |
| 环境配置文件、开发配置、部署模板 | 根目录 `env/` | 不再用根目录 `config/` 存环境文件；不提交真实凭据 |
| 配置结构、读取、覆盖与校验 | `internal/config/`；入口提供 `-check-config`，与正常启动校验同一份最终配置 | 不让业务包自行读配置；检查模式不建连、不迁移、不启动监听 |
| gRPC 方法、请求、响应 | 提供方 `contracts-<domain>/proto/`；生成代码在 `gen/go/` | 不在服务目录手写第二份相同的 gRPC 消息；不编辑生成物 |
| HTTP 绑定契约等接口资产 | 服务根 `api/`，仅有此类资产时存在 | 仓顶层 `api/policies/` 是网关聚合输入，不跟随服务 `api/` 移动 |
| 本服务的入站协议实现 | `internal/transport/<接口域>/` | **不设 `transport/grpc/`、`transport/http/` 中间层**；用 `_grpc.go`、`_http.go` 区分 |
| 本服务调用其他服务 | `internal/client/grpc/<实际目标>/` 或 `internal/client/http/<实际目标>/` | 不让调用方读取对方的配置、导入对方 `internal/` 或读取对方的库 |
| 业务、模型、持久化 | `internal/<业务>/`；复杂能力按需拆 `service/`、`model/`、`repo/` | 不再新增服务级全局 `service/`、`domain/`、`repo/` 堆放不同业务 |
| 连接和技术适配 | `internal/platform/<技术>/`；库迁移在 `internal/dbmigrate/` | 不给每个业务包单独创建连接池，不让连接包依赖业务模型 |
| 测试 | 白盒就近；独立黑盒或真实依赖测试可进模块根 `tests/`；跨仓验收由部署侧负责 | 不把 `*_test.go` 一刀切搬出，也不按测试文件名判定是否需要外部服务 |

### 1.1 业务目录如何决定

1. 先看**业务职责和数据归属**，再看文件前缀。`user_profile_model.go` 是用户主体的全局资料，归 `user/model/`；`user_compat_admin.go` 虽然也是 `user_` 开头，但属于兼容接口，归入站适配。
2. 一个小能力可以在同一 Go 包用 `<业务>_service.go`、`<对象>_model.go`、`<业务>_repo.go` 表达职责；代码复杂、需要独立边界时，再建子包。目录不会自动带来隔离：拆包后 Go 的未导出成员不再互相可见，同一个接收者类型的方法必须留在同一个包。
3. 只编排其他能力的业务没有自己的 `model/`、`repo/`。例如 `account/service` 调用户状态、凭据、MFA、会话能力；账号登录不能直接查表，也不需要为自己加连接池。
4. 状态常量优先放所属模型的 `<对象>_status.go`；跨多个子包且不该依赖模型时才设独立类型包，不预建空 `enum/`。值的定义与状态转换规则分开，后者留在业务服务。
5. 业务服务可以定义自己需要的窄接口，具体存储或出站适配由入口注入。其他业务不直接导入你的 `repo`。若已有跨表事务，应先保留完整的持久化操作，再调整依赖；不为了拆包把一次提交拆成多次。Go `internal/` 约束外部导入，**不自动禁止同一服务内的跨业务导入**。

### 1.2 HTTP、gRPC 和存储类型不要混在一起

| 文件例子 | 作用 |
| --- | --- |
| `transport/iam/user_profile_http.go` | 解码、解析身份、调用用户资料服务，返回现有状态码和响应信封 |
| `transport/iam/user_profile_http_dto.go` | HTTP 请求和响应的具名结构；字段少时可写在 Handler 同文件。只映射接口承诺的字段 |
| `user/service/user_profile_service.go` | 资料写入规则、业务输入和结果。HTTP、gRPC 都可复用，不引入 JSON 或 protobuf 协议细节 |
| `user/model/user_profile_model.go` | `UserProfile` 与 `user_profile` 的 GORM 映射，不直接序列化为外部响应 |
| `contracts-iam/proto/*.proto` | 对应 gRPC 的请求、响应和字段编号。已有 HTTP → proto 绑定的路由继续复用 proto 字段定义，不再手写一个同形状的 HTTP DTO |

例：增加个性签名时，用户资料包负责校验和保存；只有对外提供该字段的接口需要改回参。已有 JSON 键名、ID 类型、空值和省略语义保持不变；不借迁移强制统一 snake_case/camelCase，也不把管理员、本人、公开资料合成一个会泄露字段的响应类型。

### 1.3 文件名与目录模板

```text
service-<domain>/
├── cmd/<entry>/                         # 按实际入口保留
├── env/                                 # dev.yaml、<域>-prod.template.yaml 等
├── api/                                 # 可选，HTTP 绑定契约
├── internal/
│   ├── config/                          # config.go、load.go、validate.go 按需拆
│   ├── transport/<接口域>/              # <接口>_grpc.go、<接口>_http.go、*_http_dto.go
│   ├── client/
│   │   ├── grpc/<目标域>/                # <目标或能力>_grpc.go
│   │   └── http/<目标域>/
│   ├── <业务>/                          # 小能力可一包多文件；复杂能力才采用下三层
│   │   ├── service/<业务>_service.go
│   │   ├── model/<对象>_model.go
│   │   └── repo/<业务>_repo.go
│   ├── platform/<技术>/                 # db、objectstore、smtp 等按需建
│   └── dbmigrate/                       # 表注册、迁移顺序、结构校验
└── tests/
    ├── integration/<能力>/             # 独立协议或真实依赖测试
    ├── unit/<能力>/                    # 可选，刻意从外部验证公开行为的单测
    └── testkit/                        # 可选，仅测试使用的共用装配和夹具
```

文件名用小写下划线加职责后缀，例如 `message_send.go`、`user_profile_repo.go`、`file_meta_grpc.go`，测试以同主题加 `_test.go`。不叠加仓名和数据库名。现有物理库名由 DSN 决定，表名和列名由模型显式映射；`user_profile`、`im_message`、`analysis_tasks` 保留原样，目录调整不产生 DDL。

## 2. IAM：身份、用户资料与账号流程

入口：`ppb-iam/service-iam/cmd/{server,migrate,qatokens}`。对外 gRPC 契约继续使用 `ppb-iam/contracts-iam`。以下路径均相对 `service-iam/`，为迁移落点；一个旧文件混多个角色时按符号拆，不事先整文件改名。

| 现有文件或目录 | 目标文件或目录 | 职责和注意事项 |
| --- | --- | --- |
| `internal/domain/user_model.go` 中的 `User` 与 `UserProfile` | `internal/user/model/user_model.go`、`user_profile_model.go` | 用户主体与全局资料都归 `user`，**不创建顶层 `profile/`**；保留表名、字段、索引和时间语义。状态定义可单拆 `user_status.go` |
| `internal/repo/account_repo.go` 中资料/用户查询；`internal/service/account_service.go` 中资料方法 | `internal/user/repo/user_repo.go`、`user_profile_repo.go`；`internal/user/service/user_service.go`、`user_profile_service.go` | 改昵称、头像、签名进入用户资料服务；查询结果按需要投影，不返回给接口直接序列化 |
| `internal/service/account_service.go`、`account_provisioning.go` 等的流程逻辑 | `internal/account/service/account_login.go`、`account_register.go`、`account_reauth.go`、`account_ports.go` | 只编排用户状态、凭据、MFA 和会话；`account` 不建 `model/`、`repo/`，不直接持有数据库连接 |
| `internal/repo/account_repo.go` 的 `RegisterTx`、`account_provisioning_repo.go` 的 `ProvisionTx` | 通过编排层的写入接口继续调用原事务；拆出时可落 `internal/user/repo/user_registration_repo.go` | 这是受控的注册持久化操作，不是普通跨业务写表；保留用户、资料、身份、凭据及相关审计/outbox 的原提交与失败回滚范围 |
| `internal/domain/identity_model.go` 与密码、验证码逻辑 | `internal/credential/`（`model/`、`service/`、`repo/` 按需） | 登录标识、凭据验证、改密、验证码；不能因文件带 `account_` 前缀就全搬进编排层 |
| `internal/service/session_service.go`、`internal/domain/session_model.go` | 按用途分别归 `internal/session/` 和 `internal/oidc/` | IAM 会话创建、校验、撤销归 `session`；OIDC 授权事务不按旧模型文件名误归。MFA 继续是独立能力 |
| `internal/oidcstorage/`、`internal/service/signing_key.go` | `internal/oidc/` 同包按文件拆；密钥加载与过渡适配可落 `internal/keymaterial/` | `Storage` 的协议方法不能分到不同 Go 包。当前 OIDC 与 MFA 使用同一密钥材料；目录改造不得改派生或重新生成生产密钥，解耦/轮换另案 |
| `internal/handler/{iam_rpc_handler,iamx_rpc_handler,user_compat_admin,iam_http_handler}.go` | `internal/transport/iam/{iam_grpc,account_bridge_grpc,admin_compat_grpc,iam_http}.go`；按需 `*_http_dto.go` | 保留 IamService、IamAccountBridge、AdminCompat 注册及原 HTTP 契约；兼容入口只承接，不新增业务 |
| `internal/memberauth/`、`internal/platformregistry/` | 保留 `memberauth` 的成员登录/组织选择职责；平台治理相关代码归 `platformadmin/` | 全局账号不拥有 IM 组织成员资料；平台治理不直接写普通用户资料表 |
| `internal/service/iam_config.go`；`internal/repo/iam_db_connect.go` | `internal/config/`；连接归 `internal/platform/db/`，模型注册及结构检查归 `internal/dbmigrate/` | `env/iam-prod.template.yaml` 保留原模板内容；迁移配置路径时同步实际消费者 |

`preference/` 继续负责偏好，`notify/` 负责投递业务，`audit/` 负责审计；不要求这些能力一次性改名或补齐子目录。验收优先：用户资料、注册失败回滚、登录/重新认证、MFA 既有因子可用、原网关透传路由和 gRPC 注册不变。

验收优先：消息写入和回执、群/工作区隔离、联合 File 引用及元信息、好友/推送 outbox、WebSocket 路由与重连补拉。

## 4. File：文件、上传和下载

入口：保留 `ppb-file/service-file/cmd/file`。契约仍归 `ppb-file/contracts-file`。

| 现有位置 | 目标位置 | 职责和注意事项 |
| --- | --- | --- |
| `internal/handler/file_handler.go`、`file_meta_handler.go`、`file_upload_handler.go`、`file_download_handler.go`、`file_manage_handler.go` | `internal/transport/file/file_grpc.go`、`file_meta_grpc.go`、`file_upload_grpc.go`、`file_download_grpc.go`、`file_manage_grpc.go` | 注册实例及同一 `FileHandler` 的 RPC 方法保持在同一个 Go 包；启动注册仍在 `cmd/file` |
| `internal/handler/file_transfer_handler.go` | `internal/transport/file/file_transfer_http.go` | 当前与 `FileHandler` 共用接收者，包含普通/分片上传。移位与接收者同批处理，不改 HTTP 路径和签名规则 |
| `internal/domain/file_model.go`、`internal/repo/file_repo.go`、`internal/service/file_{access,upload,download}_service.go` | `internal/file/model/`、`repo/`、`service/` | 初期同归文件域；`file`、`file_blob`、`file_upload`、引用、配额的耦合先做事务核对，不一张表拆一个业务包。识别清楚独立边界后再立 `upload/` 等子能力 |
| `internal/service/file_storage.go`、`file_storage_s3.go` | 纯技术客户端归 `internal/platform/objectstore/`；文件路径授权和生命周期规则留文件域 | 不改变本地/S3 的选择、对象键、回收或清理口径 |
| `internal/rpcclient/access_grpc_client.go` 等 | `internal/client/grpc/<实际目标>/` | 按运行时调用目标归档；若 RefAccess 客户端面向多个宿主，可用 `refaccess/` 表示协议适配，不能硬编码成固定下游 |

第一条试点是 `GetFileMetasByIds`：沿 `contracts-file` → `FileHandler.GetFileMetasByIds` → `FileKeysByIds` → `FilesByIDs` → IM 的调用端做验证。由于其 Handler 有共用接收者，允许先在旧包保留薄委托或成组搬迁 Handler，不能只把一个方法移出原包。验收优先：原响应、错误码及缺项处理、上传/下载、已授权和未授权结果、IM 文件消息联调。

## 6. 共享底座、配置和测试

- **共享代码**：`ppb-base/go-framework` 负责通用日志、数据库连接、请求 ID 等；`platform-sdk` 负责稳定、可复用的跨服务客户端能力。本服务特有的映射和业务判断留本服务，不重新做全域业务共享包。
- **环境文件**：`env/` 可提交开发缺省和脱敏模板。预发/生产的 DSN、Token、私钥等由部署注入或挂载。`ppb-base/deploy/config/` 是跨仓部署侧目录，**不因为服务仓改 `env/` 就自动重命名**；若某脚本、Dockerfile、CI、文档引用了被迁文件，则与该文件同批改并验证。配置目录改名与新增环境门禁分开评审。
- **依赖接入**：对其他服务使用地址、身份配置和已发布契约。MQ、Redis、SMTP 等只给真正使用它们的服务配；App 接口的业务事件形态不随运行环境变化。
- **测试分布**：盘点时 IAM/IM/File/Camera/Gateway 的 Go 测试文件分别为 62/80/30/23/5，均随实现目录放置；Wardrobe 8 个也是就近存放，但采用外部测试包。它们是文件数，不是用例数或迁移指标。`*_test.go` 不进生产二进制；现有快速回环测试继续进默认 `go test ./...`。只有真实外部依赖需要分组时，才新增标签或专门 CI 入口，并保证至少一个流水线运行它。
- **系统验收与脚手架**：`ppb-base/deploy/scripts/verify-p2-manage.sh` 等既有验收继续由部署侧维护。试点后同步 `ppb-base/tools/templates/go-service/` 的 README 和最小示例；模板不生成空包、不要求新服务接齐所有中间件。

### 6.1 启动前配置检查（必做，先在 IAM 落地）

配置文件移入 `env/` 只是路径调整。另开配置门禁任务，解决「显式配置文件不存在仍用默认值」和「校验之后又覆盖 DSN」的问题。两项可以独立评审，不能在文件搬迁时悄悄改运行行为。

**加载顺序固定**：确定环境与配置路径 → 安全默认值 → 一份 YAML → 允许覆盖的环境变量或已挂载凭据 → 校验最终配置。IAM 现有 `internal/service/iam_config.go` 在加载时校验，而 `cmd/server/main.go` 再注入 `IAM_DB_DSN`；迁移后只校验合并完的配置。保留现有环境变量名及兼容入口，数据库连接层消费已校验的驱动和 DSN，不再另读环境变量或选择默认库。

| 任务卡 | 改动位置 | 完成条件 |
| --- | --- | --- |
| **CFG-1：IAM 加载与检查** | `internal/config/load.go`、`validate.go` 与测试；`cmd/server/main.go` 增加 `-check-config`；同步调整实际数据库连接入口 | 检查和正常启动使用同一加载与校验逻辑。检查成功退出 `0`，失败非零；检查模式不连数据库、下游或 MQ，不跑迁移、不生成密钥、不启动监听。正常启动通过后才进入既有建连、迁移和装配。 |

**校验规则**：显式 `-config` 缺失或不可读、YAML 未知字段、未知环境一律失败；预发/生产不得使用开发默认凭据或隐式回退到本地库。IAM 生产必须提供与 MySQL 驱动匹配的 DSN，校验必要凭据和签名密钥文件可读，格式与必填项错误直接失败。缺少 DSN 时不得启动成 SQLite；旧 `APP_ENV=sqlite` 如需继续兼容，在部署脚本侧映射成开发环境加显式 SQLite。错误信息只说明环境、字段和原因，不回显 Token、密钥、完整 DSN 或包含这些值的原始解析错误。
