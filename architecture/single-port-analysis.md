# 单端口分析：我们的两口 vs 字节的一口（如何调整）

> 日期：2026-11-23 · 触发问题：当前每服务两口（RPC 910x + HTTP 911x），字节内部一口，怎么调
> 关联：`adr-gateway-http-proxy.md`（两口架构的定案）、`kitex-placement-map.md`

## 一、现状实证

四服务各两口在役：RPC 口（Kitex server，gRPC 线缆：回环 + 服务间 + 测试互证）
+ HTTP 口（servicehttp 契约面，网关反代目标）。HTTP 面承载物分三类：

| 类别 | 量 | 例子 |
|---|---|---|
| JSON bind/reply 型（可 RPC 翻译） | ~130 条 | im 88（member 47+manage 37+public 4）、camera 29、file 管理 12、iam 7 |
| **HTTP 特殊语义车道（无法 bind/reply 化）** | 3 条车道 | `file_transfer`（multipart 上传/Range 流式下载/缩略图，网关直转）、im `/ws`（协议升级）、iam OIDC（浏览器重定向端点） |
| 探针 | 每服务 3 | /ping /healthz /metrics |

## 二、字节单端口的本质（公开资料 + 生态分工推断）

字节业务服务 = **纯 RPC 进程**（Thrift+TTHeader 一个口），且**能**做到单口，靠的
不是端口技巧，而是三件事把「需要 HTTP 的东西」从业务服务挪走了：

1. **HTTP→RPC 翻译收口在统一接入层**：对外 API 由网关/BFF 从 IDL 生成绑定，
   业务服务不自带 HTTP 面；
2. **大文件不走服务**：对象存储（TOS）+ 预签名 URL 直传直下，服务只发凭证——
   无 multipart/Range 流式车道；
3. **长连接与认证是专门设施**：实时接入网关独立部署；OIDC/认证门户是独立服务。

健康/指标由平台侧或 RPC 协议承载；真需要 HTTP 的进程用 Hertz 独立成服务——
那本来就是另一类服务。**单端口是「服务无 HTTP 面」的架构结果。**

## 三、我们的调整路径（按改动量）

### 路径 0：维持两口（现状，ADR 已定案）
收益已证：回环整跳 <1ms；两口成本 = 运维面（多一个监听/探针/防火墙目标）。

### 路径 C：技术性合口 —— ❌ 与框架相悖
HTTP 口 h2c 同口跑 gRPC 需 grpc-go ServeHTTP 模式（放弃 Kitex 服务端）；
Kitex detection 只收 TTHeader/KitexProtobuf/gRPC/ttstream，**无任意 HTTP handler
托管能力**（HTTP 服务是 Hertz 的领域）。不可行。

### 路径 B：增量半程 —— 收益边际
~130 条 bind/reply 路由上收网关（servicehttp 是 ppb-base 共享库、契约已声明式
7 份 JSON，网关可加载同一套做翻译+鉴权），三条特殊车道保留 → im/iam 收敛为
「RPC + 特殊口」、file 仍两口。端口 8→6，半吊子形态，不建议单独做。

### 路径 A：字节同构全量 —— 可达，但有三个硬前置
等价于把 gateway ADR 重开 + 完成字节的三件生态分工：

1. **文件传输改对象存储直传**（MinIO 预签名 URL；服务只签发凭证）→ 消灭
   `file_transfer` 车道。**这件独立有价值**：服务不再承载文件带宽；
2. **实时 WS 独立接入进程**（或网关原生长连接能力）→ im 无 HTTP 特殊口；
3. **OIDC 端点独立认证服务**（iam-web 已是独立前端，端点随门户走）→ iam 无
   HTTP 特殊口。

三前置完成后，四服务收敛为纯 RPC 单口，网关变契约网关（加载 7 份契约 JSON
做 bind/reply + 中间件），探针走 gRPC health（internalauth 豁免前缀已预留）。

## 四、量化对账

| | 值 |
|---|---|
| 收益 | 每服务 −1 监听口/探针目标；形态与字节对齐；网关获得契约视图（可做统一限流/审计） |
| 性能收益 | ≈ 0（回环 <1ms 已实测） |
| 代价 | 三前置（每件独立立项：直传改造 ≈2-3 天、WS 接入独立化 ≈2-3 天、OIDC 迁端 ≈1-2 天）+ 网关契约化 ≈3-4 天 + 鉴权中间件跨进程搬迁的安全复审 |

## 五、结论

字节的「一个端口」**不是把两口合成一口，而是把需要 HTTP 的东西从业务服务里
挪走**（翻译上收网关、文件走对象存储直传、长连接/认证独立设施）。直接合口
（路径 C）与 Kitex 相悖；跳过前置做半程（路径 B）收益边际。**建议维持两口**；
若做字节同构，按「文件直传 → WS/OIDC 独立化 → 契约上收」的顺序推进前置
（其中文件对象存储直传无论是否合口都值得做——服务带宽卸载的独立收益）。
